---
name: build-poc
description: 技術選定または実現可能性の問いに対し、実装パターンを列挙して候補と評価軸の星取表を作り、実行可能な環境の最小実験でセルを埋めて成功基準を満たす最適な候補を選ぶPoCが必要なときに使う。
---

## 手順

1. 依頼から、問い、候補、評価軸、必須条件、選好条件とその優先順位、成功基準、実行環境 (依頼が示したローカルの検証用データを含む)、許可された作成範囲、結果の出力先ディレクトリを特定する。出力先ディレクトリが未指定なら推測で決めず指定を求め、検証コードの作成範囲や作業ディレクトリを出力先とみなさない。問いを表す kebab-case の案件 slug を決め、出力先直下の `<案件slug>/` を案件ディレクトリとする。
2. 依頼が候補を絞っていても、候補が無くても、よりよい案を貪欲に探して実装パターンを列挙する。必須条件と選好条件から構成の分かれ目 (データの持ち方、計算の時機、処理を担う場所等) を挙げ、分かれ目ごとに、必須条件を満たし得て選好条件で他の候補を上回り得る実装パターンを、指定外のものも含めて候補にする。分かれ目と、各選択肢が候補になるか、ならない理由を星取表の脚注に記録する。
3. 候補を行、評価軸を列とする星取表を、候補が一つでも実験前に作る。各セルは `○` (観測した合格)、`△` (条件付き合格。条件と影響を添える)、`×` (観測した不合格)、`未検証` のいずれかで、観測済みのセルには根拠を添える。観測と推定を分け、調査、推定、予想だけのセル (実験前の表は全セル) は `未検証` とする。
4. 観測値と公開された上限から計算した値は、式を脚注に記録して観測として扱う。依頼が利用可能と示していないデータや環境を作って代替した観測 (合成データ、縮小規模、模擬環境等) は、判断主体が代替を受け入れるまで `未検証` とし、観測値は代替の内容とともに参考値として脚注に記録する。
5. 各列に必須か選好かを示し、必須の列は合否の閾値を列見出しに書く。`○`、`△`、`×` は閾値を持つ列にだけ使い、閾値のない選好条件の列は相対順位と実測値で埋める。数値条件の測定単位と除外する費用は、実験前に脚注で固定する。
6. 解釈によって記号、順位、結論が変わる多義的な条件は、解釈ごとに列を分けて観測し、依頼文言に忠実な解釈を必須の列として確定を判断主体に求める (全解釈で結論が変わらないときに限り、確認を待たず完了できる)。選定に使う選好条件とその優先順位が依頼に無ければ、同じく表の設計時に確定を判断主体に求める。
7. 出力先が未確定の間は、星取表と観測記録を回答本文に保持し、確定後に `poc.md` へ移す。未確定のまま終えるなら、書き出せない事実と `poc.md` に入れる内容の全量を回答で返す。出力先が確定したら、存在確認と同じ呼び出しで案件ディレクトリを作成し、同名が既にあれば書き込まず別名か追記の指示を求める。実験の前に `poc.md` へ `## 問い` と `## 星取表` を書き、以後は実測に合わせて節単位で更新し、全文を書き直さない。
8. 作成と変更は許可された局所対象に限る。検証用ブランチの push と、元のブランチ (開始時のブランチ) を base とする draft PR は、この skill の起動が承認を含むので、依頼が外部状態の変更を禁じない限り行う。それ以外の外部状態の変更は、変更先と内容が承認された場合だけ行う。
9. 書き込みや操作の確認は、その呼び出しの末尾で結果を出力して確かめ、確認だけの turn を作らない。同じ実験や操作を繰り返すのは、状態が変わった根拠があるときだけにする。
10. 実験の実行前に、許可された作成範囲の内側に生成物の除外を設定する。許可されたインターフェースに対し、結論を左右するセル (指定外の候補のセルを含む) に絞った最小の局所実験を実行し、結論を変えないセルまで埋めるために実験を広げない。測らない候補は、許可された範囲で測れない理由 (未承認の外部状態の変更、費用、操作を要する場合は、測定内容を判断主体に提案する)、または観測済みのセルから結論を変えないと言える理由を添えて行に「測らない」と記録し、`×` にしない。
11. 依頼に無い測定入力は seed 等で決定的に固定して脚注に記録し、その妥当性の確定を判断主体に求める事項として申し送る。
12. 実験後は、観測済みの必須条件が `×` の候補を棄却し (測らない候補は対象外)、必須条件が全て観測済みの `○` または `△` の候補を依頼の優先順位の高い選好条件から順に比べて順位付けし、最上位の一つを推奨候補とし、暫定採用として示す。該当する候補が無ければ推奨を示さない。推奨が指定外の候補でも、採用の確定は判断主体に求める。
13. 完了、no-go、中断のいずれで終わっても検証コードを保全する。リポジトリのルートが変更を許された領域の外にあるか、リポジトリが無ければ、ブランチも commit も作らず、対象リポジトリ無しとして扱う。
14. 対象リポジトリがあれば、人が書いた検証コードのファイルだけを、元のブランチから切った検証用ブランチ `poc/<案件slug>` に commit し、元のブランチと元の作業ツリーには残さない (専用の worktree を使ってよい)。ブランチ作成、commit、push、draft PR は 1 回の呼び出しで順に実行し、操作ごとの終了コードと URL をその出力から記録する。remote や PR 作成手段が無いと読み取りで分かった操作は試行せず対象なしとし、失敗した操作はローカルブランチ名と失敗内容を記録して続ける。
15. `poc.md` は未完了でも結果で仕上げ、同じ呼び出しの末尾で内容を出力して保存を確かめる。見出し `## 問い`、`## 星取表`、`## 結論`、`## PR`、`## 申し送り` を持ち、測定条件、試行別の観測値 (試行の同一性を判断できる形で)、未検証事項を含める。`## 結論` には、PoC の完了可否、推奨候補 (該当が無ければ無し)、推奨の根拠となるセル、推奨が前提にする `△`・解釈・受け入れ済みの `未検証`、候補ごとの棄却理由 (測らない候補は測らない理由)、推奨が覆る条件を記す。
16. `## 結論`・`## 申し送り`・回答の文章で `未検証` のセルや候補に触れるときは、未検証であることと不足する証拠だけを述べる。参考値、仕組みからの推測、見込みや有望さの評価は星取表に置く。列挙した候補は測らなかったものも `## 星取表` に置く。
17. `## PR` には draft PR の URL を記録する。できなかったときはローカルブランチ名と失敗内容、対象リポジトリ無しのときは検証コードの所在を記録し、元の作業ツリーに検証コードを残置したときはその事実と除去手順も記録する。`## 申し送り` は、新しいセッションのプロトタイプ作業が `poc.md` だけで前提を再構成できる自己完結した内容とし、判断主体の決定を待つ事項 (採用承認、選好条件の確定、未承認の測定等) を承認待ち事項として明記する。

## 完了

PoC は、推奨候補の全必須条件が観測済みの `○` か、判断主体が条件と影響を明示的に受け入れた `△` で、結論を覆し得る `未検証` が無いとき、または全候補が観測済みの必須条件で棄却されて no-go を判断できるときに完了する。結論を覆し得るセルは、必須条件と、候補間の選定に実際に使う選好条件のセルである。そのセルが `未検証` か条件が未承認の `△` のとき、または選好条件や優先順位が未確定で順位が決まらないときは完了とせず、不足する証拠、追加測定の条件、必要な判断主体の決定を `## 申し送り` に書く。

PoC の完了可否 (`## 結論`) と判断主体の承認待ち事項 (`## 申し送り`) は、別々に書く。採用が承認され、残る問いがコードベースとの配置、責務、慣習、契約の適合性だけになったときに限り、プロトタイプへ進めると判断する。実現可能性が未解決なら PoC を続け、全候補を棄却したなら停止するか新候補を求める。

回答には、`poc.md` のパス、星取表、結論、PoC の完了可否、承認待ち事項、PR の URL または失敗、未検証事項、次に担うべき責務を返す。プロトタイプへ進めると判断した場合は、後続作業への入力が `poc.md` のパスであることを明記し、別 skill は暗黙に起動しない。回答の文章も、推測を星取表にだけ置く規則に従う。
