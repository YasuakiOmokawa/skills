---

## 手順

1. 依頼、タスクの文脈、リポジトリから、現在の計画と実装済みの変更を特定する。`## Acceptance Criteria`、`## MECE Review`、`## Verification Plan` がそれぞれちょうど一つあることを求める。空行を除けば、Acceptance Criteria 節は、コロンの後に空白以外の基準テキストを持つ、一意で厳密な `- [ ] AC-NNN:` 行を一つ以上だけ含まなければならない。MECE Review はちょうど一つの `- AC IDs:` 行とちょうど一つの `- Gate:` 行を含まなければならず、ID の値は現在の ID を `, ` で連結した昇順で列挙し、gate の値全体は `- Gate: ready` である。Verification Plan は同一の値を持つちょうど一つの `- AC IDs:` 行を含まなければならない。空行とその AC-ID 行を除けば、Verification Plan は現在の AC ごとにちょうど一つの `### AC-NNN` エントリだけを含み、他のエントリを含んではならない。空行を除けば、各エントリは空でない `- Oracle:`、`- Evidence anchors:`、`- Prerequisites:`、`- Required effects:` 行をそれぞれちょうど一つだけ含まなければならない。検証を開始してよいかを判断する前に、列挙したすべての構造条件を検査する。いずれかの条件を満たさない場合は、実装後に要件を再構成せずに停止し、検出したすべての stale または不正な条件を報告する。
2. 過去の検証レポートは手法のヒントとしてだけ扱い、決して現在の結果として扱わない。チェックの前に、厳密な現在の計画、現在の `HEAD`、整列したファイル単位のリポジトリ記録から、決定的な fingerprint を一つ取得する。untracked のディレクトリはファイルまで展開する。staged の各パスについては index の状態、mode、blob の digest または削除マーカーを記録し、unstaged または untracked の各パスについては working tree の状態、ファイル種別、mode、内容の digest または削除マーカーを記録する。一部だけ staged のパスは両方の記録を保持する。機密の内容は報告しない。すべてのチェックの後に同じ fingerprint を再取得する。完全な検証エントリをそれぞれ、その AC の契約として使う。required effect は現在の依頼が承認する場合だけ実行し、そうでなければ基準を未検証のまま残し、欠けている承認を述べる。
3. リポジトリのスクリプト、テスト、ドキュメント、fixture、API、データベースクエリ、ログ、描画されたインターフェースを調べ、各基準について許可された中で最も強い直接観測を特定する。既存の仕組みを優先し、最小限のローカル probe は承認されかつ必要な場合だけ作る。
4. 実行可能なすべてのチェックを実行する。状態を持つ振る舞いについては、操作の前後で該当する状態を比較する。描画された UI の振る舞いについては、必要な表示条件を設定し、実際のページを操作する。ソースの調査、HTTP の成功、操作の送信は視覚的な根拠ではない。
5. 観測した結果が oracle と一致する場合だけ基準を PASS、oracle と矛盾する場合は FAIL、許可された根拠がどちらも確定させない場合は未検証とする。他の基準が失敗しても各結果を保持する。
6. すべての FAIL をその根拠から診断する。根本原因が実装にあり、その修正が元の承認の範囲内に収まる場合は、失敗に範囲を絞った最小の修正を行い、失敗した基準と、その修正が影響し得る以前に通ったチェックを再実行する。新しい根拠が別の承認された修正を特定する間だけ続ける。効果のなかった試みの繰り返し、要件の変更、範囲の拡大、未承認の操作の前に停止する。修正を行った場合は、最後の修正の後に開始時の fingerprint を取り直し、すべての基準をその状態で確認し直す。最後の修正より前に得た結果は経過として報告するが、完全な検証の根拠にしない。
7. 利用できない環境または一時的な依存先については、利用可能で文書化された安全な復旧を試す。それでも必要な観測ができない場合は、基準を未検証のまま残し、完了に必要な厳密なアクセス、サービス、認証情報、データ、または操作を述べる。
8. 可能な場合は一時的な probe を除去し、検証で作ったデータを復元する。残留物や外部状態の変化があれば報告する。
9. 計画または現在の依頼がコードレビューまたは指摘の適用を含む場合は、渡された範囲内の最新の出力から指摘台帳を特定する。両方が渡された場合は、最新のレビュー出力を指摘の集合とし、それに対応する適用出力を、一致する項目への処置と根拠の更新として使う。一方の活動が範囲外の場合は、もう一方の出力だけを使う。項目ごとの結果は保持するが、critical または major の指摘が未解決、先送り、またはその影響を受ける使用をカバーする新たな直接チェックなしに適用されている間は、完全な検証を認めない。範囲内の出力が利用できない場合は、その前提条件を未検証として報告する。両方の活動が範囲外の場合は、指摘台帳を求めも報告もしない。
10. 開始時の fingerprint (修正を行った場合は最後の修正の後に取り直したもの) と終了時の fingerprint を比較する。不一致があればその実行は stale となる: すべての基準の結果は保持するが完全な検証を認めず、変化した計画またはリポジトリの入力を報告する。両方の fingerprint、すべての基準の手法、観測、結果、すべての修正と再実行、残るすべての失敗または未検証の前提条件、そして手順9が該当する場合に限り指摘台帳の gate を報告する。完全な検証を主張するのは、すべての基準が通り、fingerprint が一致し、該当する指摘の gate に阻害要因が無い場合だけである。検証は、依頼が承認していない commit、push、pull request、外部の変更を承認しない。
