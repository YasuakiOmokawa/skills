## 目的

実装済みの変更を、計画の受け入れ基準ごとに直接観測して判定し、完了か否かを言う。

## 原理

- oracle による受け入れ判定: 各 AC は Verification Plan の oracle と照らし、観測が一致すれば PASS、矛盾すれば FAIL、許可された観測で確定できなければ未検証とする。許可された中で最も直接的な観測 (テスト、API、DB、ログ) を行い、コードを読んだだけ、HTTP の成功や操作の送信だけでは観測にならず、状態を持つ振る舞いは操作の前後を比べる。過去の結果を今回の結果に再利用せず、他の AC の結果に関わらず各結果を保つ。
- 種類ごとの観測: `[振る舞い]` は外の境界を通して観測する。`[禁止]` は check_plan.py の禁止の検査 (見本の出し入れを含む) の結果で判定する。CI や deploy の後でしか観測できない基準は、結果が無ければ未検証とする。
- 判定と修正の分離: FAIL は観測した根拠と原因の所在 (実装の不足、define-done の欠陥、要求、環境) を報告し、直さない。AC が要求を満たせないと分かったら、計画の直し案を返さず、要求の見直しが要ることと根拠だけを返す。define-done の欠陥なら define-done のやり直しが要ると返す。環境の不備も製品コードで回避せず未検証とする。

## 契約

- 入力: 実装済みの差分と、current plan の `## Acceptance Criteria` と `## Verification Plan` (`### AC-NNN` ごとの `- Oracle:`、`- Evidence anchors:`、`- Prerequisites:`、`- Required effects:`)。あれば実画面検証の結果と、指摘台帳 (指摘適用の出力)。差分が無ければ検証しない。検証の前に、この skill の dir の `scripts/check_plan.py` を `python3 <script> check-green <計画> <repo>` で流す。exit 1 で `forbidden:` 以外の検査の行があれば、実装から補わず検証を一件も実行せず、出力と define-done のやり直しが要ることを報告する。exit 1 の `forbidden:` の行は、その `[禁止]` の AC の FAIL とする。
- 検証方法は依頼者に尋ねず、Evidence anchors を起点にリポジトリから解決する。UI の AC は、渡された実画面検証の結果を根拠にし、無ければ未検証とする。
- 指摘台帳の critical/major のうち、未解決、先送り、または適用済みでも影響を受ける振る舞いを今回直接観測していないものを完了の妨げとする。計画に実在する記述を引用した不採用と、観測した根拠による前提不成立は解決済みとする。
- 出力: 完了か否かの結論を先頭に置き、完了でなければ commit や PR などの後続に進めないと添える。続けて、AC ごとの手法・観測・結果を返す。残る FAIL、未検証、完了を妨げる指摘ごとに、確認した不足条件と、誰が何をすれば埋まるか、片付け残しを返す。

## 禁止

- 製品コード、計画、AC、Verification Plan を変えない (script による見本の一時的な出し入れは除き、許可も要らない)。
- Required effects は今回の依頼が許可した操作とだけ照合し、計画の記述を許可の根拠にしない。許可の無い操作を要する AC は未検証とする。
- 承認されていない commit、push、PR 作成、外部状態や本番データの変更をしない。一時 probe と検証データは片付ける。
- 効果の出ない同じ試みを繰り返さない。

## 完了条件

完了と言えるのは、全 AC が PASS で、完了を妨げる指摘が無いときだけである。
