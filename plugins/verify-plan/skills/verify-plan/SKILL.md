## 目的

実装済みの変更を、define-done が封をした受け入れテストと計画の受け入れ基準ごとに直接観測して判定し、完了か否かを言う。

## 原理

- 封の受け入れテストによる判定: テストを持つ AC は、封の時点で落ちていた受け入れテストが今の tree で通るかだけで判定する。テストの AC-ID ごとに全件 pass なら PASS、1 件でも fail なら FAIL、許可された環境で流せなければ未検証とする。コードを読んだだけ、過去の結果、他の AC の結果を今回の判定に使わない。
- 回帰: 既存の test suite を流し、封の時点で通っていて今落ちるテストを回帰の FAIL とする。
- テストの無い AC: define-done がテストを書けなかった AC (実画面、CI や deploy の後でしか観測できないもの) は、許可された中で最も直接的な観測で判定する。UI は渡された実画面検証の結果を根拠にし、無ければ未検証とする。CI や deploy の結果が無ければ未検証とする。
- 判定と修正の分離: FAIL は観測した根拠と原因の所在 (実装の不足、define-done の欠陥、要求、環境) を報告し、直さない。AC が要求を満たせないと分かったら、計画やテストの直し案を返さず、要求の見直しが要ることと根拠だけを返す。環境の不備も製品コードで回避せず未検証とする。

## 契約

- 入力: 実装済みの差分、define-done が封をした計画、あれば実画面検証の結果と指摘台帳 (指摘適用の出力)。差分が無ければ検証しない。
- 検証の前に、この skill の dir の `scripts/check_seal.py` を `python3 <script> check <repo>` で流す。exit 1 なら検証を一件も実行せず、出力 (封が無い、または封の後に受け入れテストか計画が変わった) と、define-done のやり直しか変更の取り消しが要ることを報告する。
- 続けて `python3 <script> at-seal <repo>` で受け入れテストを封の時点の tree で流す。`at-seal-exit: 0` (封の時点で既に通っていた) なら、テストが振る舞いを観測していないので define-done の欠陥として報告し、完了としない。依存が無いなどで封の時点の tree で流せなければ、その確認を未検証とする。既存の test suite も `at-seal <repo> -- <コマンド>` で封の時点の結果を取り、回帰の判定に使う。
- 検証方法は依頼者に尋ねず、`test-command:` と repo から解決する。外部状態の変更を要する観測は、今回の依頼が許可した操作とだけ照合し、許可の無いものは未検証とする。
- 指摘台帳の critical/major のうち、未解決、先送り、または適用済みでも影響を受ける振る舞いを今回直接観測していないものを完了の妨げとする。計画に実在する記述を引用した不採用と、観測した根拠による前提不成立は解決済みとする。
- 出力: 完了か否かの結論を先頭に置き、完了でなければ commit や PR などの後続に進めないと添える。続けて、封の確認の結果、AC ごとの手法・観測・結果、回帰の結果を返す。残る FAIL、未検証、完了を妨げる指摘ごとに、確認した不足条件と、誰が何をすれば埋まるか、片付け残しを返す。

## 禁止

- 製品コード、計画、受け入れテストを変えない。
- 承認されていない commit、push、PR 作成、外部状態や本番データの変更をしない。一時 probe と検証データは片付ける。
- 効果の出ない同じ試みを繰り返さない。

## 完了条件

完了と言えるのは、封の確認が exit 0 で、封の時点で受け入れテストが落ちていて、全 AC が PASS で、回帰が無く、完了を妨げる指摘が無いときだけである。
