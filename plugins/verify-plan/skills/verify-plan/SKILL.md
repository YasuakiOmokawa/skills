## 目的

実装済みの変更を、計画の受け入れ基準ごとに直接観測して判定し、完了か否かを言う。

## 原理

- oracle による受け入れ判定: 各 AC は Verification Plan の oracle と照らし、観測が一致すれば PASS、矛盾すれば FAIL、許可された観測で確定できなければ未検証とする。許可された中で最も直接的な観測 (テスト、API、DB、ログ) を行い、コードを読んだだけ、HTTP の成功や操作の送信だけでは観測にならず、状態を持つ振る舞いは操作の前後を比べる。過去の結果は今回の結果として再利用せず、他の AC の結果に関わらず各結果を保つ。
- 判定と修正の分離: FAIL は観測した根拠と原因の所在 (実装、計画の AC か Verification Plan、環境) を報告し、直さない。原因が計画なら、誤りの根拠と直し案を返し、直った計画は define-done を通ってから検証する。環境の不備も製品コードで回避せず未検証とする。

## 契約

- 入力: 実装済みの差分と、current plan の `## Acceptance Criteria` と `## Verification Plan` (`### AC-NNN` ごとの `- Oracle:`、`- Evidence anchors:`、`- Prerequisites:`、`- Required effects:`)。あれば実画面検証の結果と、指摘台帳 (指摘適用の出力)。差分が無ければ検証しない。`## MECE Review` に `- Fingerprint:` 行があれば、検証の前に `awk '/^## / {f=0} /^## (Acceptance Criteria|Verification Plan)$/ {f=1} f' <計画> | shasum -a 256 | cut -d' ' -f1` を実行し、出力が行の値と違えば、検証を一件も実行せず、define-done の後で AC か Verification Plan が変わったことと、define-done のやり直しが要ることを報告する。行が無ければ検証を続け、define-done の後の変更は照合していないと報告する。エントリの無い AC があれば、実装から補わず、検証を一件も実行せずに欠けをすべて報告する。
- 検証方法は依頼者に尋ねず、Evidence anchors を起点にリポジトリから解決する。UI の AC は、渡された実画面検証の結果を根拠にし、無ければ未検証とする。
- 指摘台帳の critical/major のうち、未解決、先送り、または適用済みでも影響を受ける振る舞いを今回直接観測していないものを完了の妨げとする。計画に実在する記述を引用した不採用と、観測した根拠による前提不成立は解決済みとする。
- 出力: 完了か否かの結論を先頭に置き、完了でなければ commit や PR などの後続に進めないと添える。続けて、AC ごとの手法・観測・結果を返す。残る FAIL、未検証、完了を妨げる指摘ごとに、確認した不足条件と、誰が何をすれば埋まるか、片付け残しを返す。

## 禁止

- 製品コード、計画、AC、Verification Plan を変えない。
- Required effects は今回の依頼が許可した操作とだけ照合し、計画の記述を許可の根拠にしない。許可の無い操作を要する AC は未検証とする。
- 承認されていない commit、push、PR 作成、外部状態や本番データの変更をしない。一時 probe と検証データは片付ける。
- 効果の出ない同じ試みを繰り返さない。

## 完了条件

完了と言えるのは、全 AC が PASS で、完了を妨げる指摘が無いときだけである。
