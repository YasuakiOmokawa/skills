## 目的

承認済みの PoC または同等の根拠で選ばれた方式が、コードベースの責務、慣習、契約に適合するかを実コードで確かめ、結果を Design Doc 作成が読める形で残す。

## 原理

- 適合性の検証: 従う慣習とその根拠の規則を実ファイルから確認する。境界案は実ファイルの類似例か承認された案に限り、配置、責務層、依存方向、契約の組で同定し、実際の変更と振る舞いの観測で適合を判断する。判断には根拠の実ファイル、変更箇所、観測結果、責務または依存方向の一致、逸脱時の具体的影響を揃える。技術は成立するが不適合なら、失敗した案から配置、責務層、依存方向、契約のいずれかを変えた案だけを一候補一回試し、範囲外の候補を発明しない。棄却ごとに実行観測と実ファイルの根拠のどちらによるかを記録する。
- 選定理由の保存: 定量的な根拠は同一環境内の候補間比較で検証し、PoC 環境の絶対値の再現を求めない。選ばれた理由が組み込み後も成立していることを適合の条件に含める。不適合が選定を覆すなら PoC へ戻し、適合する複数案か逸脱を選ぶ規範的判断だけが残るなら Design Doc へ渡す。

## 契約

- 入力: 承認済みの `poc.md`。`## 問い`、`## 星取表`、`## 結論`、`## 申し送り` を承認済みの根拠とし、そのファイルを追記先、親ディレクトリ名を案件slugとする。パスが無ければ依頼中の同等根拠で続行し、追記先が無い事実と、対象コードのパスと機能名から導出したslugの根拠を報告する。同等根拠に選定理由が無ければ未検証事項とし、適合判断を条件付きにする。
- 承認済み契約の外で観測した差のうち、実証済み振る舞いの前提か既存の呼び出し側に触れるものはテストで固定し、残る設計判断として `## Prototype` に併記する。それ以外は観測記録に留める。
- 変更の保全: 適合、不適合、中断のいずれでも、対象コードと検証コードの変更だけを元のブランチから切った `prototype/<案件slug>` ブランチに commit・push し、元のブランチを base とする draft PR を作る。元のブランチと元の作業ツリーには残さない。リポジトリが無い、またはルートが変更を許された領域の外なら、ブランチも commit も作らず変更をその場に残す。この skill の起動は push と draft PR の承認を含む。依頼が外部状態の変更を禁じるときは行わない。
- 出力: `poc.md` の末尾に `## Prototype` 節を追記し、既存節を変えない。変更箇所、振る舞いと適合性ごとの確認結果、完了可否、Design Doc へ進める可否、残る設計判断、制約、失敗、未検証事項を、このファイルだけで前提を再構成できる形で書く。`### PR` には draft PR の URL、作れなかったときはブランチ名と失敗内容、リポジトリ無しのときは理由と変更の所在を書く。追記先が無ければ同じ内容を回答で返し、保存できない事実を報告する。

## 禁止

- 上記以外の公開や外部状態の変更は、変更先と内容が承認された場合だけ行う。
- 編集を許された範囲の外を変更しない。必要なら着手せず報告する。
- 成功を確かめられなかった push や PR 作成を、状態変化の根拠なく繰り返さない。
- 別の skill を暗黙に起動しない。

## 完了条件

- 期待する振る舞いと適合性の問いを観測し、適合か不適合かを判断した時点で完了する。振る舞いが通るだけでは Design Doc へ進めない。
- Design Doc へ進めるのは、選定方式が既存コードベースに適合し、設計を覆し得る適合性の未検証事項がない場合に限る。意図的な逸脱を渡すときは、適合する範囲内の代替案を試したかリポジトリ上の根拠で棄却し、逸脱の具体的影響と判断主体を示す。これは逸脱の承認、本番品質、展開、運用準備の完了を意味しない。
- 新しいセッションが `## Prototype` 節と `### PR` から変更にたどり着き、再利用できる。
- 再読取などで確かめていない書き込みを成功と報告しない。
- 回答には `poc.md` のパス、`## Prototype` 節の要旨、次に担う責務を返す。Design Doc へ進めるなら後続への入力は追記済みの `poc.md`、追記先が無ければ回答本文の `## Prototype` 節とする。
