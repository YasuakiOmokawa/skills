## 目的

コメント、boolean、nullableな戻り値、I/Oに埋もれた判断に置かれた意図を、名前、直和型、全域関数、テストへ移す。

## 原理

- 意図はコードの構造に置く: 渡されたコードのコメント、boolean、nullableな戻り値、boolean引数、インラインの判断を全て、次の順で決める。コードが既に言っているなら削除する。改名、結果型、sum type、名前付き定数、関数抽出、assertion、テストでコードへ移してから削除する。コードが表せないこと (外部仕様、他所の不具合の回避、明白な代替案を退けたトレードオフ) だけ残す。整合を保つべき別の箇所にこのコードを結び付けるコメントは、共有シンボルかテストになるまでは表せない制約なので、テストへ移すか残す。コメントを残す前に、その性質を述べる名前か単位を述べる型エイリアスを試し、全てを言い表せたら削除する。コメントが無くても不明瞭な名前と責務に同じ順序を適用し、最小の再構成と改名を実際に行う。
- 何かが消えるときだけ足す: 新しいテストは、削除したコメントの意図か依頼が明らかにした制約を保つためだけに足す。I/Oを行う関数 (storeやリクエストをawaitする、時計や乱数源を読む) から判断を純粋関数や述語へ切り出すのは、今あるものが消えるときだけ: 既存テストが要するfake・層・注入された依存、同じ判断の2つ目のコピー、関数内の時計や乱数の読み取り。既存テストが自明なstubで判断をカバー済みなら、新しい関数で書けるテストや1行の条件に付く名前は数えない。何も消えないなら1行の述語でもその場に残し、説明していたコメントはテスト名かassertionへ移し、候補として報告する。業務上の意味を持つI/Oの順序は呼び出し側に残す。純粋なコード内で、コメントの内容を名前が担うヘルパーへの移動は正当である。

## 契約

- 入力: 整理するコードと依頼。編集してよいファイルを示す依頼はそのファイルを承認する。整理対象を名指すだけの依頼は、変更する名前、型、シグネチャへの作業ツリー内の全参照 (exportを含む) も承認し、呼び出し側、テスト、テスト名を同じ変更で更新する。
- 外部の出典 (仕様の節、インシデント、契約条項、他システムの振る舞い) を引く既存コメントは、テストが固定していてもその箇所に1行残す。依存先 (言語、ライブラリ、実行環境) の保証に頼るコメントは代替案を退けた理由だけ1行残し、型を含む保証を確かめ直すテストは足さない。残したコメントに対のテストは付けない。「残す」判断は渡されたコードに既にあるコメントにだけ効く。
- 名前は指す対象を字義どおりに述べ、コードベースに初めて触れる読み手が名前だけで分かるものにする。既存・追加を問わず全ての識別子とテスト名で、慣用句、比喩、業界やチームのjargonを字義どおりの語に言い直す。各語は単独での通常の意味で判断し、識別子が保持または返すリテラル値が変えてはならない観測出力でも識別子は改名する。明瞭な名前は変えない。
- 結果、状態、引数、「処理済み」の値の型付けを変える前、`throw` を置き換える前に、[references/types.md](references/types.md) を読みその規則を適用する。
- 出力: 確認したdiff、残した各コメントとコードがそれを表せない理由、適用しなかった抽出やbrandとその理由、type checkと振る舞い確認の結果、範囲外の再構成、未検証のまま残る振る舞い。

## 禁止

- commit、push、PR作成、外部状態の変更をしない。
- 承認されていない対象を変えない。承認されていない対象を要する再構成は適用せず報告する。
- 機能やポリシーの変更 (コメントやTODOが求める変更を含む) をせず、整理の外に置いて報告する。振る舞いを保つ。
- 整理の間にコメントを追加しない。依頼や編集で判明した制約は、理由を名前で述べるテストかassertionで固定し、どちらでも保持できなければコメントに書かず報告する。
- リポジトリや利用者の規則、ADR、固有の慣用と衝突する移動は適用せず報告する。

## 完了条件

設定済みのtype checkと渡された振る舞い確認を、特定した境界ケースを含めて実行し、変更前と比べた結果を報告したとき完了する。
