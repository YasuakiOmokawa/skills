# プラン修正・追記フォーマット

MECE 分析完了後の出力先は **分析ファイル**（`{プランファイル名}.analysis.md`）。
プランファイル本文には品質検証サマリー 1 行のみ追記する。

main agent は取得済み BB / WB と Red Team の **JSONLines 出力**をパースし、本フォーマットに従って **Markdown** に変換して分析ファイルに書き出す。欠落ロールは JSONL で補わない。

## 修正ルール

| 重要度 | 対応 |
|--------|------|
| 🔴 Critical | 下記セクションに記録 + プラン内の該当箇所（セクション名・内容）と推奨修正内容を併記 |
| 🟡 Important | 下記セクションに追記のみ（プラン本文は変更しない） |
| 🟢 Nice-to-have | 下記セクションに追記のみ（プラン本文は変更しない） |

**finding ID をプラン本文に持ち込まない**: 指摘をプラン本文へ反映する後続作業では、`BB-N` / `WB-N` / `IM-N` / `M-N` 等の finding ID や「（MECE 指摘 IM1）」型の出典注記を書かない。指摘内容は該当セクションへ展開し、出典は `## 品質検証` の分析ファイル参照 1 箇所に集約する。

## 分析ファイルへの upsert セクション

既存の `## MECE分析結果` があれば次の同レベル見出し直前または EOF までを置換し、常に1節だけ保持する。

```markdown
## MECE分析結果

### 分析サマリー
- 分析日時: YYYY-MM-DD
- 対象リポジトリ: ${REPO_NAME}
- 実行メタ: tier=[standard/deep] / dispatch [D]体 (D = 起動した independent executor 数。tier を上流記録から上書きした場合は理由を括弧内に併記する)
- ACカバレッジ: N/M項目充足
- 漏れ件数: X
- 重複件数: Y
- 判定: MECE OK / 要修正（Critical N件）
- 未取得ロール: [BB / WB と理由。全取得時はこの行ごと省略]
- 判定不能 (Unknown): [Red Team 出力に「判定不能 (Unknown)」がある場合、理由付きで列挙。0 件ならこの行ごと省略]
- レビュー範囲外: [Red Team が関与シグナルなしとした一般領域を1行で列挙。なければ省略]
```

**分析サマリーの集計定義 (本ファイルが SSOT)**:
- **漏れ件数**: Red Team が独自検出した `お見合い` の件数 = **`M*` と `T*` の合計** (checklist は M / T を対象領域で排他に振り分けるため単純合算)。**severity 問わず全件、ただし 1 件のお見合いを Critical に昇格させても M* で 1 件のみカウント (二重計上禁止)**。standard で Red Team を skip した場合は `0件 (Red Team skip のため未検出)` と注記付きで表記する (数値スロットへの括弧注記は許容)。Unknown は漏れ件数・Critical のいずれにも計上しない独立軸で、ある場合は `漏れ件数: N (+ Unknown K 件は未確定)` と併記する
- **重複件数**: 4 分類クロスリファレンス表で **「真の合意」+「補強し合う合意」の合計件数**
- **Critical 件数**: 統合 Critical 指摘の件数 (severity Critical のみ)。**漏れ件数と Critical 件数は独立に集計** (Critical 昇格お見合いは漏れに 1 件 + Critical に 1 件カウントするが、別軸の集計なので二重計上違反にはならない)

### 4分類クロスリファレンス (area タグで機械集約)

```markdown
### 4分類クロスリファレンス (area タグで機械集約)
| # | Area | BB 指摘 ID | WB 指摘 ID | 分類 (真の合意/補強合意/実装漏れ/仕様漏れ/お見合い) | 統合 Severity | 統合内容 |
|---|------|------|------|------|---------|---------|
```

**分類の意味**:
- **真の合意**: BB と WB が同じ問題を**同じ層**から発見 (両方仕様 or 両方コード)
- **補強し合う合意**: BB と WB が同じ問題を**異なる層**から発見 (信頼度最高)
- **実装漏れ**: 仕様にあるがコードにない (BB 充足 WB 言及なし)
- **仕様漏れ**: コードにあるが仕様未記載、または暗黙の前提 (BB 言及なし WB 充足)
- **お見合い**: 両 Analyst が言及ゼロ、Red Team が独自検出

**集約は area タグで機械化**: 同じ `Area` 値を持つ BB/WB 指摘を peer 候補として並べ、Issue 本文で意味的一致を判定する。

**「お見合い」行の合成手順 (main agent)**: Red Team 出力の `class` 値は `真の合意` / `補強し合う合意` / `実装漏れ` / `仕様漏れ` の 4 値で、お見合いは別 JSONLines (`M1, M2, ...`) として出力される。これを 4分類クロスリファレンス表の「お見合い」行に統合する:

1. Red Team 出力 `M*` JSONLines を読む (`id`, `area`, `perspective`, `content`, `severity`)
2. 各 `M*` を 4分類クロスリファレンス表に新規行として追加: `BB 指摘 ID = null`, `WB 指摘 ID = null`, `分類 = お見合い`, `統合 Severity = M*.severity`, `統合内容 = M*.content (perspective: M*.perspective)`
3. `T*` (純技術リスク補完) は「純技術リスク補完」表にのみ載せ、4分類クロスリファレンス表へは転記しない。ただし漏れ件数には `M*` と合算で算入する (上記「分析サマリーの集計定義」が SSOT)

**お見合い M* と AC カバレッジ表の関係**:
- **既存 AC に紐付く** お見合い (例: AC-7「/admin/* 非影響」が両者言及なし) → AC カバレッジ表で総合「不十分」+ 4 分類クロスリファレンス表でも「お見合い」行として両方に出す
- **既存 AC に紐付かない** お見合い (例: Red Team 独自検出の rate-limit / cleanup 等) → 4 分類クロスリファレンス表のみに「お見合い」行として出し、`[MECE追加]` AC として AC カバレッジ表の末尾に追加する

### ACカバレッジ検証結果 (main agent が BB / WB の AC 判定から機械合成)

```markdown
### ACカバレッジ検証結果
| AC-ID | AC項目 (短く要約) | カテゴリ | BB 判定 | WB 判定 | 総合判定 |
|---|--------|---------|--------|---------|---------|
| AC-1 | ... | 正常系/異常系/エッジ/不変条件/非影響 | 充足/不十分/言及なし/未取得 | 充足/不十分/言及なし/未取得 | 充足/不十分/言及なし |
```

**機械合成手順** (main agent):
1. dispatch 時に AC を `AC-1, AC-2, ...` で序数付けて subagent に渡す
2. 取得済み BB / WB の「AC 判定」テーブル (AC-ID + 判定) を AC-ID で join。空ロールは各行 `未取得` と表示し、JSONL 行を合成しない
3. synthesis-and-errors.md Step 3-1 のマージルール (SSOT) に従って総合判定列を算出
4. 元 AC 文の「カテゴリ」(正常系/異常系/エッジ/不変条件/非影響) を分析ファイルの AC セクションから引いて補完

**ACカバレッジ N/M の定義**: M = **全 AC 項目数 (`[MECE追加]` を含む)**、N = M のうち総合判定が「充足」となった項目数。実行開始時から存在する tagged rows も通常どおり enumerate して BB/WB 判定を使う。現在の Step 3-2 で analyst pass 後に新規追加した `[MECE追加]` だけは元 AC の最大番号の続きで採番し、main agent が3判定列を `未判定` として N に含めない。`未判定` はこの合成行だけの例外で、Analyst JSONL の `judgment` には使わない。現在の実行で書き換えた `[MECE追加 変更]` は元 AC として1回だけ数え、変更後スコープ未検証を注記する。

**`[MECE追加]` 比率 X/M (品質指標)**: 全 AC のうち MECE 検証で追加された項目数 X の比率。X は5つの canonical category にある全 `[MECE追加]` を数える (`[MECE追加 変更]` と無タグ補足は数えない):

- `X/M ≤ 10%`: 元 AC が十分網羅的
- `X/M = 10〜30%`: 一定の漏れあり
- `X/M > 30%`: 観点選択が大きく外れていた可能性
- **M < 10 の小規模 AC では比率でなく件数で読む** (母数が小さいと数件の追加で 30% を超え、指標が実態と釣り合わない)

```markdown
### Critical指摘（要修正）
| # | 指摘 | プラン該当箇所 | 推奨修正内容 | 根拠 (BB/WB/Red Team) | 4分類 |
|---|------|--------------|------------|------|---------|

### Important / Nice-to-have
| # | 重要度 | 指摘 | 推奨対応 | 根拠 | 4分類 |
|---|--------|------|---------|------|---------|

### お見合い検出 (Red Team 独自)
| # | 領域 | チェックリスト観点 | 発見事項 | Severity |
|---|------|---------|---------|---------|

### 純技術リスク補完 (Red Team が BB/WB 盲点を補完)
| # | 観点 (セキュリティ/パフォーマンス/依存) | 発見事項 | Severity |
|---|------|---------|---------|

### 各ロール出力 (JSONL)
<details>
<summary>BB / WB findings + AC 判定 (JSONL)</summary>

${BB_JSONL}

${WB_JSONL}

</details>
```

**元 Markdown 全文は転記しない**: BB / WB / Red Team の Markdown 部 (Self-report 等) の `<details>` 全文転記は、分析ファイル肥大と main agent のコンテキスト保持コストの主因だったため廃止済み。Red Team の JSONL は上の 4分類クロスリファレンス表・お見合い表・純技術リスク表・Critical/Important 表へ合成済みのため転記せず、Markdown 部から転記するのは「判定不能 (Unknown)」のみ (SKILL.md Step 3-3)。

**Critical=0 (MECE OK) の場合の省略規則**: 表の列構成は上記の標準テンプレートが SSOT であり、Critical=0 でも `Area` 列・`AC-ID` 列は削らない。省略してよいのは (a) `### Critical指摘（要修正）` テーブル (0 件のため節ごと省略可)、(b) Important / Nice-to-have が 0 件の場合のそのテーブル、(c) Red Team skip 時のお見合い表・純技術リスク表 (空のまま「Red Team skip のため未検出」と明記)。

## プランファイルへのサマリー追記

プランファイルの `## 品質検証` セクションに **1 行だけ** upsert する（セクションがなければ作成）:

```markdown
- MECE判定: [OK (Critical: 0) or 要修正（Critical N件）] / Important [I]件 (うちAC反映 [R]件) → [分析ファイル名]
```

`I` / `R` の定義は [synthesis-and-errors.md](synthesis-and-errors.md) の「サマリー値の定義 (SSOT)」。カバレッジ・漏れ・重複・Unknown の詳細集計は分析サマリー側にのみ記録する。

## AC ブラッシュアップの運用ルール

### `[MECE追加]` タグの適用範囲

| ケース | タグ | 書き方 |
|---|---|---|
| 新規 AC 項目を追加 (仕様漏れ・お見合いから) | `[MECE追加]` | 対応する5カテゴリの既存セクションへ追記する。正常系/異常系は `- [ ] [MECE追加] <controlled label>: ...`、エッジケースは `- [ ] [MECE追加] <controlled label> [境界値: <カテゴリ>]: ...`、不変条件は `- [ ] [MECE追加] [不変条件: <パターン>]: ...`、非影響確認は `- [ ] [MECE追加] [既存機能名]が...`。enumerate の `- AC-N (...)` は内部形式なので書き戻さない |
| 既存 AC を具体化（補足を加えるだけ） | タグ不要 | 元 AC 行の末尾にカッコ書きで補足 |
| 既存 AC を修正（書き換える） | `[MECE追加 変更]` | チェックボックス直後に `[MECE追加 変更]` を置き、その後は元カテゴリの上流書式を保って修正理由を併記 |

**専用サブセクション（`### [MECE追加] 新規AC項目` 等）は作らない**。正常系 / 異常系 / エッジケース / 不変条件 / 非影響確認のいずれかに根拠付きで分類できる項目だけを既存カテゴリへ追記する。分類不能なら AC を発明せず `判定不能 (Unknown)` と理由を `## MECE分析結果` に残す。

### 「充足」判定の基準 (機械的に決定)

Analyst が見た AC の判定と ACカバレッジ表の「総合判定」は `references/synthesis-and-errors.md` Step 3-1 のマージルール (SSOT) で機械決定する (総合値は `充足` / `不十分` / `言及なし` の 3 値のみ、絵文字エイリアス禁止)。`未取得` は空ロール列だけの表示状態で、Analyst judgment や総合値には使わない。Analyst pass 後に当回追加した AC の合成行だけは上記 N/M 定義どおり `未判定` とする。

### 「カバレッジ不十分」と「AC 自体の不備」の分類フロー (4 分類との対応)

```
発見した問題は何か?
├─ AC は明確だが、プラン / 実装方針で対応されていない (BB 充足 WB 言及なし = 実装漏れ)
│   → 「Critical 指摘」に記録 + プラン側を修正
├─ AC の記述が曖昧、または重要要件が暗黙 (BB 言及なし WB 充足 = 仕様漏れ)
│   → 「AC ブラッシュアップ」で `[MECE追加]` または既存 AC 具体化
├─ 両者言及ゼロで Red Team が検出 (お見合い)
│   → 「AC ブラッシュアップ」で `[MECE追加]` + Critical 候補なら指摘も記録
└─ BB と WB が同じ問題を別角度で発見 (真の合意)
    → 「Critical 指摘」に統合 1 件として記録 (重複カウントしない)
```

判別の例:
- 「過去版をダウンロードできる」AC があり、プランに権限チェック実装の記述なし (BB 充足) → コードに権限チェックなし (WB 充足) → **真の合意 Critical**
- 「DB トランザクションでロールバック」AC があり、コードに transaction なし (BB 充足 WB 言及なし) → **実装漏れ Critical**
- コードに soft-delete scope があるが AC に削除済ユーザの扱い記述なし (BB 言及なし WB 充足) → **仕様漏れ、AC に `[MECE追加]`**
- BB / WB 両者言及ゼロの XXE 攻撃を Red Team が検出 (お見合い) → **AC に `[MECE追加]` + Critical 指摘**
