# 非影響確認カテゴリ

## (a) 手動列挙

観点と紐付けず、変更コードが触れる隣接機能を該当件数だけ記述する。正常系・異常系・エッジケースで既に検証する主対象を重複させない:
```markdown
### 非影響確認
- [ ] /api/health エンドポイントが影響を受けないこと
- [ ] 既存認証 middleware の挙動が変わらないこと
```

## (b) git diff 隣接ファイル列挙 (自動補完)

プランで変更が宣言されたファイル群の隣接ファイル (同ディレクトリ・呼び出し先) を `git diff --name-only` 系コマンドで列挙し、それぞれの非影響を確認:

```bash
git diff --name-only $(git merge-base HEAD main)..HEAD | xargs dirname | sort -u
# → 影響範囲となる隣接ディレクトリを抽出、その他のテストが落ちないことを確認
```

## (c) 省略

変更が完全に独立 (例: 新規ファイルのみ追加で既存への変更ゼロ) なら `### 非影響確認` を残し、本文に省略理由を書く。判断根拠は `### 検討観点` にも 1 文で記録する。

## (a)/(b)/(c) の機械判定基準 (裁量判断を排除)

`git status --short` (もしくは `git diff --name-status $(git merge-base HEAD main)..HEAD`) を実行し、出力で機械判定:

| `git status` 出力 | 判定 |
|---|---|
| `M` (modified) が 1 件以上 | **(a) または (b) 必須** (既存への影響あり) |
| `A` (added) のみ | **(c) 省略可** |
| `D` (deleted) を含む | **(a) 必須** (既存削除は影響範囲調査が必要、自動列挙の (b) では不十分) |

判定結果と判断根拠を分析ファイル `### 検討観点` に 1 文で明記 (例: `git status: M 2 / A 1 → (b) 隣接ファイル列挙を選択`)。

**部分 payload 送信**: 既存 update/PATCH の payload を参照実装より縮小する変更は (a) 固定。削ったキーの未送信時挙動を nested attributes / 汎用 setter のサーバ側代入まで確認する。

**plan mode (git 実行不能) のフォールバック分類**: `git status` / `git diff` が取れない (plan mode で未着手 / 別リポジトリ) 場合、plan 本文の「変更ファイル予定」記述から種別を推定する — 「〜追加 (新規ファイル作成)」= `A` 相当 → (c) 省略可、「既存ファイルへの追記 (バリデーション追加 / ルート追加 / アクション追加 等)」= `M` 相当 → (a) 必須、「〜削除」= `D` 相当 → (a) 必須。不明なら安全側で `M` 相当とする。判定根拠に `(推定)` を付す (例: `plan 推定: 既存 controller へ action 追加 = M 相当 → (a) 手動列挙`)。
