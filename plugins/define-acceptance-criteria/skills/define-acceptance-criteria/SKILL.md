## 目的

既存の計画や仕様を、成功、失敗、境界、非影響の振る舞いを判定できる受け入れ基準に変換し、保存先の計画に書く。

## 原理

- YAGNI: 計画が採用した範囲 (目的、仕様、変更対象) の振る舞いだけを基準にし、その観測方法を定める計画内の記述 (レビュー指摘を含む) は基準に反映する。範囲を超える新しい振る舞いの推奨や別チケットの項目は範囲外として返す。資料が決めていない値 (境界点を含む) は、依頼が決めるよう求めても不足情報に分け、決まっている条件だけを基準にする。
- oracle で判定できる基準: 範囲内の成功、失敗、境界、非影響の各条件を、一つの前提または操作と呼び出し側から観測できる一つの結果を対にした独立の基準にする。境界はすぐ両側の観測で判定し、同一に見える必要があるケースは両者の観測を比べる基準にする。コマンドや検索を oracle にする基準は、書く前に現在のツリーで実際に実行して変更前に red (非影響なら green) を確かめ、検索に当たる行が変更後も残る行 (計画が残す行、他の基準が作らせる test や文書) なら走査対象を絞る。リポジトリ全体の検索は、未追跡も含めた `git grep` のように、`.gitignore` が無視する生成物を走査しない形で書く。文書への追加は、識別子と置き場所で観測し、文は後の推敲で変わるので全文の一致は求めない。全条件を基準に MECE に対応付け、漏れ、重複、同時に成立しない組があれば書き直すか不足情報に分ける。

## 契約

- 入力: 書き込み可能な計画の受け入れ基準を求める依頼。その計画が保存先になる。
- 保存先の唯一の `## Acceptance Criteria` 節に、1 行 1 件の `- AC-NNN: ...` の行と空行だけを置く。対応表や注記は別の `##` 節に置く。後続は `## Acceptance Criteria` と `AC-NNN` を読む。
- ID は既存が無ければ `AC-001` から、あれば既存の最大より大きい番号を付ける。既存の基準は ID ごと保持し、意味が変わったものだけ旧 ID を再利用せず新しい ID の基準で置き換える。
- 既存の `## MECE Review` と `## Verification Plan` は書き換えず、それぞれの `- AC IDs:` 行が新しい AC-ID の集合と食い違えば stale と報告する。
- 最終回答は、基準、条件と基準の対応 (基準の無い条件の有無を明示)、実行結果、範囲外の項目、未確定の範囲、書き込み結果、stale な下流の節、未検証事項を返す。

## 禁止

- 書き込みは保存先の計画に限り、test、製品コード、外部状態を変更しない。
- 保存先の基準に無関係な内容を消さない。

## 完了条件

- 全条件が基準、不足情報、範囲外のいずれかに分かれている。
- 再読取で確かめていない書き込みを成功と報告しない。拒否や失敗ではその事実と計画が変わっていないことを報告する。
