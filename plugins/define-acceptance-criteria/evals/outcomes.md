# Trigger
- fixture: 書き込み可能な current plan として `plans/reset.md` があり、仕様は「登録済みメールには三十分有効な再設定リンクを送り、未登録メールにも同じ受付画面を見せ、既存セッションへ影響させない」とする。依頼Aは「このプランの受け入れ基準を作って」、依頼Bは「自動テストを実装して」である。
- assertions:
  - [critical] 依頼Aでは観測可能な受け入れ基準を作る。
  - [critical] 依頼Bではテストコードを作成しない。
  - [critical] 依頼Aでは `plans/reset.md` の唯一の `## Acceptance Criteria` へ AC-ID 付きで反映する。
  - 依頼Aで成功、失敗、時間境界、非影響を対象にする。
  - 仕様にない製品要件を追加しない。

# Outcome
- fixture: パスワード再設定仕様では、登録済みメールと未登録メールの送信後はいずれも登録有無を示さない同じ受付画面へ遷移し、「受付が完了しました」と表示する。登録済みメールへ届くリンクは発行後二十九分五十九秒では利用でき、三十分一秒では期限切れ画面となってパスワードを変更しない。初回利用では再設定が成功して既存セッションを維持し、同じリンクの再利用では「このリンクは使用済みです」と表示してパスワードを変更しない。
- assertions:
  - [critical] 各条件を操作と観測結果が一意になる基準へ変換する。
  - [critical] 三十分の直前と直後を境界として扱う。
  - [critical] 各基準を `AC-001` から始まる安定したIDへ対応付け、既存IDを振り直さない。
  - 登録済みと未登録で受付画面が同じであることを検証可能にする。
  - 既存セッションが維持される非影響を独立した基準にする。

  - [critical] 製品コードと外部状態を変更しない。

# Hold-out

- fixture: current plan の `AC-004` は「期限後は変更しない」を意味するが、更新仕様は「期限後は新しいリンクを発行する」へ意味を変更し、その更新が許可されている。
- assertions:
  - [critical] 確定している期限と受付画面の受け入れ基準を作る。
  - [critical] 再送上限を推測せず、不足情報として分離する。
  - 不明な上限に対する合格条件を創作しない。
  - 完成した範囲と未確定範囲を報告する。
  - [critical] 意味が変わった基準へ `AC-004` を再利用せず、新しいAC-IDを割り当てる。
  - AC-ID集合が変わることで既存のMECE ReviewとVerification Planをstaleにする。
