## 目的

承認済み計画と PoC・プロトタイプの根拠から、実装者が単独で読んで実装判断できる Design Doc を指定文書に書く。

## 原理

- 単独で読める: 実装者が PoC 結果ファイルや会話履歴を読み返さずに各実装判断を行えるよう、必要な前提と契約を本文へ転記する。主要フロー、失敗時の扱い、確認方法、データ、保持、移行、展開、運用は常に該当する観点とし、本文の規範的記述はすべて承認済み計画、取得できた根拠、承認済み判断、未解決判断のいずれかに対応付ける。「該当なし」と理由を書いた節も対応付けに数える。
- 観測・承認・未承認・未解決の区別: 観測済みの事実、承認済みの判断、未承認の提案または仮定、未解決判断を混ぜない。承認済みと扱うのは、承認者が人間として明示された判断と、依頼者本人がこの依頼の中で値や方式を決めた判断だけで、後者では氏名の有無を論点にしない。依頼が前提として与えた承認済み計画は、承認者が未記載でも採用する。依頼者自身が未合意と述べた案と前工程の完了判定は承認と書き分け、設計承認を代行しない。根拠どうしが同じ規範的記述について異なる配置や値を示すなら、一方を採用せず衝突を未解決判断にし、両観測が共通して満たす性質と決着に必要な証拠を分けて記す。必要成果物が排他的に変わる差は止める側、併存可能な差は止めない側とする。採らない配置から機能、データ、保持、移行の不存在を推論せず、根拠に一切の言及がない適用可能項目は関連するものをまとめて 1 件の未解決判断にしてよい。採らない代替案は根拠にあるものだけを書き、無ければ創作せず比較根拠が無いと書く。未解決判断には、判断主体 (同定できなければ未同定とし、その同定を必要な決定に含める)、必要な証拠または決定、実装を止めるか、止める範囲と止めない範囲 (コード実装と本番展開を分ける) を付け、止めるものを先頭に個別記載する。実装を止めるとは承認済み計画の中核成果物に着手できないことで、計画の文面が未決の値で構造を決めると明記する成果物 (テーブル定義やスキーマ) は、他の部分が着手できても止める側、移行・展開・運用だけが止まる項目は止めない側にする。

## 契約

- 入力: プロトタイプ追記済みの `poc.md`。`## 問い`、`## 星取表`、`## 結論`、`## PR`、`## 申し送り`、`## Prototype` を根拠として読む。指定文書が無ければ同じディレクトリの `design-doc.md` を出力先とする。
- テンプレートが未指定なら `~/.claude/skills-config/create-design-doc/dd_template.md` と `~/.claude/skills-config/create-design-doc/dd_reference.md` を読む。無ければ承認済み根拠だけで続行して縮退を報告し、原理の観点を節構成とする。節見出しは省略しない。計画の対象に該当しないと根拠から分かる節は、未解決判断にせず「該当なし」と理由を 1 行で書く。根拠が無いだけで該当が分からない節は、不存在を推測せず対応する未解決判断を参照する。
- PoC とプロトタイプの draft PR は URL で参照する。URL が無ければ創作も省略もせず、その事実と原因、保全ブランチなど代替の所在を書く。
- 出力: 指定文書と、保存先、文書化できた範囲、設計判断と根拠、採らない代替案、未解決判断 (判断主体、未同定ならその旨) と実装への影響、不足する証拠、文書作成の完了可否と実装準備の可否、実施しなかった項目とその理由、失敗、未検証事項、次に担うべき責務を含む回答。

## 禁止

- 指定文書以外へ書かない。製品コードと外部文書庫を変更せず、既存の無関係な節を置換しない。
- 根拠に無い値や結果を設計事実として足さない。未解決の値を創作しない。
- 別 skill を暗黙に起動しない。

## 完了条件

指定文書を書き、全文を再読取して、書いた内容と一致し既存の無関係な節が不変であることを確かめた結果を報告したとき、文書作成は完了する。確かめていない書き込みを成功と報告しない。設計が実装可能になるのは、実装を止める未解決判断が無く、必要な人間の設計承認を確認できた場合だけで、保存成功をそれに読み替えず、自ら承認しない。
