# クロスリファレンス置換の詳細機構

SKILL.md Workflow §3 で remedy を「参照される長文 = アンカーリンク置換」と決めた後の具体機構、および「対象がソースコードコメントの場合」の canonical 選定手順をここに集約する。remedy の分岐判断 (長文=アンカー / 線形短文=言い換え / コードコメント=削除・短参照) は SKILL.md §3 が SSOT。

## アンカーリンク置換の例

```markdown
<!-- Before -->
重要な設計判断: AuthGateway は単一の責務に閉じ込め、ユーザ管理や権限管理は別サービスに委譲する。

<!-- After -->
**設計判断**: §[重要な設計判断](#重要な設計判断) 参照
```

## 置換時の注意

- セクション参照は markdown アンカーリンク `[表示文字列](#anchor)` 形式
- 参照は **その PR セクションの冒頭近く** に置く (実装の前に設計を読ませる)
- 章の段構成は SKILL.md §3 が SSOT (アンカー参照を残す章は「スコープ 1 文 + 設計判断リンク + 実装ファイル table」の三段、全文包含で段落削除した章は二段)。どちらでもスコープ説明までは削らない (過 DRY 防止)
- **関連が弱い PR の扱い**: PR の内容が SSOT に直結しない場合、**default は省略** (リンクを貼らない)。関連性が補完的に有用なら 1 句で関連性を補足。迷ったら省略 (過リンク防止を優先)
- **既存表記スタイルの維持**: 元文書が散文ならそのまま散文で残す (表記スタイル変更は別 task)
- **AC / checklist 内のクロスリファレンス**: 括弧書き `(<参照テキスト>参照)` は括弧構造を保ちつつ中身をアンカーリンクに置換 (例: 元 `(Token rotation の挙動表参照)` → `(§[Token rotation 挙動表](#token-rotation-挙動表) 参照)`)

## anchor 生成規則

`[表示文字列](#anchor)`。anchor 生成規則: ASCII を小文字化 → 空白をハイフン化 → 記号 (`§ : / . ( )` 等) と先頭/末尾の空白を除去 (日本語文字は残す)。例: 見出し `## §設計詳細` → `#設計詳細` / `## Token rotation: 挙動表 (v2)` → `#token-rotation-挙動表-v2`。生成後は SKILL.md §5 検証で実リンク疎通を確認 (記号入り見出しはずれやすい)。

## 対象がソースコードコメントの場合

- canonical の置き場所は、最も文脈が濃い箇所 (定義本体または主要呼び出し元) を 1 箇所選ぶ。コードコメントと md 文書が同一概念で重複する混在ケースでは、md 側に既存の専用セクションがあればそれを canonical とし、コード側コメントは全てそこへの短い参照に統一する
- md 側の候補セクションが複数ある場合 (ADR の「背景」と「根拠」の両方に同じ説明があるなど) は、決定・主張を正当化する側の節 (根拠) を canonical とし、前置き側の節を非正本として始末する
- 他のコメントは markdown アンカーリンクでなく「削除」または「短い参照 1 文」に置換する (grep で正本へ到達できるなら削除可 — SKILL.md §3 のコードコメント分岐と同じ規則)
- 残す参照 1 文の雛形は `# <ゴール要約 1 文> (設計詳細: <正本のファイルパス>)`。参照先は grep で到達できる形 (ファイルパス / 識別子) だけを書き、正本側の節名やアンカーは書かない (読者は正本の節構成を知らない)
- dry-run レポート (SKILL.md §4) は行範囲でなく `grep` 結果 (ファイルパス:行番号) で重複箇所を示す
- 実行順序: コメントを名前/型/定数へ蒸留できるかの判断が先 (`/express-intent-in-code` の T3。判断を済ませれば足り skill の起動は必須でない)、蒸留し切れず残ったコメントの重複集約を本 skill が後に行う
