## 目的

未 commit または未公開の変更を、レビュアーが順に読める境界の commit にまとめる。

## 原理

- atomic commit: 各 commit はレビュー可能な一つの目的とその依存 (実装はそのテストと同じ commit) を持ち、独立な変更は分け、読む順に並べる。境界は時系列を復元せず、読み手のための物語として作り直す。計画が作業項目ごとの変更対象を記録していれば、それを境界の既定にする。1 commit にするのは、計画にも変更自体にも分割線が無い場合に限り、分割のコストだけでは該当しない。commit メッセージには、その commit でレビュアーが何を見ればよいかを書く。
- 内容の保存: 境界を作り直しても内容は変えない。最終 commit の tree は、作業前の worktree (untracked を含み、除外した変更を除く) の tree と一致する。

## 契約

- 入力: 現在のブランチと base、依頼が承認した書き換えの範囲、あれば計画。未 commit の変更は常に範囲内、既存の未公開 commit は明示的に承認された場合だけ範囲内とする。
- 出力: 結論を先頭に、commit を読む順に各 commit の目的とファイル、tree 一致の結果、1 commit にした場合はその理由、除外した変更とその理由を返す。範囲内で境界を満たせず書き換えを保留したときは、承認が無いだけの未公開 commit と、書き換えられない公開済みの commit とを区別し、それぞれのブロッカーと書き換えを伴わない進め方を返す。push と PR 作成を行っていないことを明示し、tree が一致したときだけ後続作業として残す。

## 禁止

- 公開済みまたは共有済みの commit は、許可されていても書き換えず、force-push もしない。
- 承認されていない既存の commit を書き換えず、承認されていない変更や範囲外の変更を commit に含めない。
- 対話的ツール (`git add -p` など) を使わない。境界をまたぐファイルは、`git diff` から切り出した hunk patch を `git apply` で index に stage して分ける。
- 依頼が承認していない push と PR 作成をしない。

## 完了条件

全ての変更が、tree 一致を確かめた commit、除外した変更、保留した書き換えのいずれかに分かれたとき完了する。tree が一致しなければ成功と報告せず、取りこぼしを戻して再検証するか、失敗として報告する。
