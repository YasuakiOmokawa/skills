# 手順

1. 利用可能な文脈から現在のブランチとその base ブランチを特定し、worktree と、base に対する変更全体を調べ、どの commit が公開済みまたは共有済みかを記録する。
2. commit の境界は時系列からではなく読み手のために作る。各 commit をレビュー可能な一つの目的とその依存で定義し、実装はそのテストや fixture と同じ commit に置き、承認されているが互いに独立した範囲内の変更は分け、承認されていない変更や範囲外の変更は除外し、レビュアーが読むべき順に commit を並べる。現在の計画が commit 単位の change map を記録している場合は、それを分割仕様として使う。1 commit にするのは、計画にも変更自体にもレビュー可能な分割線が無い場合に限り、その理由を記録する。分割のコストだけでは該当しない。
3. 依頼が承認した履歴だけを書き換える。未 commit の worktree の変更は常に範囲内、既存の未公開 commit はその書き換えが明示的に承認された場合だけ範囲内とし、公開済みまたは共有済みの commit は決して書き換えない。force-push は決して行わず、公開済みまたは共有済みの履歴を書き換えるために force-push を使うことも決してしない。その範囲内で境界を満たせない場合は、書き換えを保留して各ブロッカーを示し、未公開履歴の書き換えに対する承認の欠如と、書き換えられない公開済み履歴とを区別して、それぞれに書き換えを伴わない安全な進め方を示す。
4. 承認された範囲のローカル履歴を境界に一致させる。worktree が未 commit の場合、または未公開履歴が混在している（修正が境界をまたいで入り組んでいる）場合は、時系列を復元するのではなく新しい物語を合成する。未公開ブランチをその merge base へ soft-reset し、選択的な staging で commit を積み直す。境界をまたぐファイルは、`git diff` の出力から切り出した hunk patch を `git apply` で index に stage して分割し、対話的なツールは決して使わない（`git add -p` / `-i` は使えない）。各 commit メッセージには、その commit でレビュアーが何を見ればよいかを書く。
5. 報告の前に確認する。最終 commit の tree が最後に確認した tree とビット単位で一致すること（`git diff <verified-ref>` が空）を必須とする。各中間 commit が確認を通ることは、リポジトリが個々の commit を残す形で PR を取り込む（rebase / merge commit）場合に限って必須とし、squash merge では終点の一致で足りる。結果の commit 順序と各 commit の diff を境界に照らして確認する。
6. 確認済みの commit 境界を読む順に、各 commit の目的とファイルとともに報告する。あわせて、1 commit にした場合はその理由、tree 一致の結果、保留した書き換えがあればそのブロッカーと安全な進め方を報告する。依頼が push と PR 作成を承認していない限り、それらは依頼者の後続作業として残す。
