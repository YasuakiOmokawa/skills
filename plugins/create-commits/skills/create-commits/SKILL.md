---

## 手順

1. 現在のブランチと base を特定し、どの commit が公開済みまたは共有済みかを書き換えの前に記録する。
2. 境界は時系列を復元せず、読み手のために新しい物語として作る (入り組んだ未公開履歴も同じ)。各 commit はレビュー可能な一つの目的とその依存 (実装はそのテストと同じ commit) を持ち、独立な変更は分け、承認されていない変更や範囲外の変更は除外し、読む順に並べる。1 commit にするのは、計画にも変更自体にもレビュー可能な分割線が無い場合に限り、その理由を記録する。分割のコストだけでは該当しない。
3. 書き換えは依頼が承認した履歴だけに行う。未 commit の worktree の変更は常に範囲内、既存の未公開 commit は明示的に承認された場合だけ範囲内とする。公開済みまたは共有済みの commit は、許可されていても決して書き換えず、force-push も決して行わない。
4. 範囲内で境界を満たせないときは、書き換えを保留して各ブロッカーを示す。承認が無いだけの未公開 commit (承認があれば再構成できる) と、書き換えられない公開済みの履歴とを区別し、それぞれに書き換えを伴わない安全な進め方を示す。
5. 書き換えと commit の前に、除外する変更を除いた worktree 全体 (untracked を含む) の tree id を検証済み tree として記録する。`GIT_INDEX_FILE="$(mktemp -u)" sh -c 'git read-tree HEAD && git add -A && git reset -q HEAD -- <除外 path> && git write-tree'` が出力する id がそれで、除外する path が無ければ `reset` の段を省く。
6. 承認された未公開 commit があれば最後の公開済み commit (無ければ merge base) へ soft-reset して戻し、未 commit の変更とあわせて選択的な staging で境界の commit に積み直す。境界をまたぐファイルは、`git diff` から切り出した hunk patch を `git apply` で index に stage して分割し、対話的ツールは使わない。各 commit メッセージには、その commit でレビュアーが何を見ればよいかを書く。
7. 確認は最後の commit と同じ呼び出しの末尾で、`[ "$(git rev-parse HEAD:)" = <検証済み tree> ] && echo TREE_MATCH || git diff-tree -r HEAD <検証済み tree>` を出力して判定する (確認だけの turn は作らない)。tree が一致しなければ成功と報告せず、取りこぼしを戻して再検証するか、失敗として報告する。
8. 依頼、計画、リポジトリ内の規約が個々の commit を残す取り込み (rebase / merge commit) を指定しているときだけ、各中間 commit がリポジトリ指定の checks を通ることを実行して確かめる。通らない境界は直して手順 7 から再検証し、直せなければ失敗として報告する。指定が無ければ (squash merge を含む) 取り込み方式を外部に照会せず、終点の tree 一致で足りる。

## 完了

全ての変更が、tree 一致を確認した commit、除外した変更、保留した書き換えのいずれかに分かれたとき完了する。結論を先頭に、確認済みの commit を読む順に、各 commit の目的とファイルを報告する。あわせて、tree 一致の結果、1 commit にした場合はその理由、除外した変更とその理由、中間 commit の確認で失敗した境界、保留した書き換えがあればそのブロッカーと書き換えを伴わない安全な進め方を報告する。依頼が push と PR 作成を承認していない限り、それらは行っていないことを明示し、tree が一致したときだけ依頼者の後続作業として残す。
