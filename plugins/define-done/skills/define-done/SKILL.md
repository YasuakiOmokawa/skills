## 目的

既存の計画について、何をもって完了とするかを、依頼が求める要求と既存の保証だけに根拠付けた受け入れ基準 (AC) として計画に書き、各 AC を、repo の既存のテストと見分けがつかない受け入れテストに翻訳し、実装の前に規則の基準が落ち非影響の基準が通ることを確かめる。AC は外から観測できる振る舞いだけで書き、計画が新しく作る規則の基準と、壊してはならない今の振る舞いの非影響の基準に分ける。規約は AC にせず、計画の決定と実装の選び方を縛らない。

## 原理

- 段の順序: 最初に 3 段の規則をすべて読み、この順に行う。前の段が書いたものを次の段の根拠にする。
  1. 要求と既存の保証: [references/requirements.md](references/requirements.md)
  2. 受け入れ基準と網羅: [references/acceptance-criteria.md](references/acceptance-criteria.md)
  3. 受け入れテスト: [references/acceptance-tests.md](references/acceptance-tests.md)
- 止めるのは 3 段目だけ: 1〜2 段の未決の判断、不足情報、範囲外、未検証は、その段の節に書いて次の段へ進む。Gate が ready でなければ、受け入れテストを書かず Gate の理由と ready にするための不足条件を報告して止まる。
- 問い返し: 依頼に「問い返し」とあれば [questions.md](references/questions.md) に従う。それ以外では読まない。
- 外部の状態: repo の test command と開発の手順がローカルで起動するもの (DB、コンテナ、アプリのサーバ) は起動してよく、テスト用の DB へ migration を流してよい。自分が起動したものは最後に止める。接続と送信はローカルの中に限る。起動できないものが要るテストは書かず未検証にする。

## 契約

- 入力: 書き込み可能な既存の計画と、依頼・計画が名指しする仕様とコード。計画が無いか全体を読めないときは何も書かず、その欠陥を報告する。
- 出力: 計画にそれぞれ唯一の `## Requirements`、`## Ground Review`、`## Acceptance Criteria`、`## MECE Review` と、作業ツリーに書いた受け入れテスト (既存のテストへの追記か、手本に倣う新しいファイル)。commit は作らない。AC が 0 件ならテストを書かない。実装の完了は repo の test command が通ることで判定する。この skill の起動は、上のローカルの起動の承認を含む。
- 最終回答: 先頭に `## Requirements` の要求を引用付きで 1 件 1 行で並べ、利用者が抜けを確かめられるようにする。続けて Gate、書いた節とテストのファイル、書き込みを確かめた方法と結果、種類別の AC 数、テストを確かめた AC、試作の patch の path を返し、空でない書き直した既存のテスト、新しく作ったディレクトリ、未決の判断 (既定と行き先を添える)、不足情報、範囲外、未検証、実装が足すテストを 1 件 1 行で並べる。該当の無い種類は書かない。受け入れテストの後の作業も求める依頼では、その報告の先頭に置く。Gate が ready でなければ、受け入れテストを書いていないので計画は実装の入力を満たさないと書く。

## 禁止

- 計画の 4 節以外の行、製品コード、既存のテストと補助の行、設定、外部状態を変えない。足してよいのは受け入れテストと、それに要る補助と期待値で、書き直してよい既存のテストは要求が振る舞いを変えるものだけである。commit も push もしない。見つけた不足や上流の修正を自分で反映せず、それで Gate を ready にしない。
- 書き込みに失敗しても、別の保存先へ迂回せず、同じ書き込みを再試行しない。
- 資料が決めていない値と未解決の前提を推測で埋めない。既定 (決めない) と行き先 (要求の持ち主) を添えて不足情報にする。計画の決定だけを根拠にした AC を作らない。

## 完了条件

3 段を終えて `check_done.py check <repo>` が exit 0 を返したか、AC が 0 件か手本が無くてテストを書かなかったか、3 段目に入る前に Gate を理由に止まった。確かめていない書き込みを成功と報告しない。
