## 目的

既存の計画について、何をもって完了とするかを、依頼が求める要求と既存の保証だけに根拠付けた受け入れ基準 (AC) として計画に書き、各 AC を実行できる受け入れテストに翻訳して、後から変えれば git の差分に必ず出る凍結の commit にする。AC は外から観測できる振る舞いだけで書き、計画が新しく作る規則の基準と、壊してはならない今の振る舞いの非影響の基準に分ける。規約は AC にせず、計画の決定と実装の選び方を縛らない。

## 原理

- 段の順序: 最初に 3 段の規則をすべて読み、この順に行う。前の段が書いたものを次の段の根拠にする。
  1. 要求と既存の保証: [references/requirements.md](references/requirements.md)
  2. 受け入れ基準と網羅: [references/acceptance-criteria.md](references/acceptance-criteria.md)
  3. 受け入れテストと凍結: [references/acceptance-tests.md](references/acceptance-tests.md)
- 止めるのは 3 段目だけ: 1〜2 段の未決の判断、不足情報、範囲外、未検証は、その段の節に書いて次の段へ進む。Gate が ready でなければ、受け入れテストを書かず Gate の理由と ready にするための不足条件を報告して止まる。
- 問い返し: 依頼に「問い返し」とあれば [questions.md](references/questions.md) に従う。それ以外では読まない。
- 外部の状態: repo が開発用に示すローカルの DB とコンテナは起動してよく、テスト用の DB へ migration を流してよい。自分が起動したものは最後に止める。ローカルの外への接続と送信、アプリのサーバの起動はしない。起動できないものが要るテストは書かず未検証にする。

## 契約

- 入力: 書き込み可能な既存の計画と、依頼・計画が名指しする仕様とコード。計画が無いか全体を読めないときは何も書かず、その欠陥を報告する。
- 出力: 計画にそれぞれ唯一の `## Requirements`、`## Ground Review`、`## Acceptance Criteria`、`## MECE Review` と、種類ごとに分けた受け入れテストのファイルと土台と、`scripts/check_seal.py seal` が作る凍結の commit。AC が 0 件なら凍結しない。実装の完了は `scripts/check_seal.py verify <repo>` の exit 0 で判定する。この skill の起動は、凍結の commit と上の DB とコンテナの操作の承認を含む。
- 最終回答: 先頭に `## Requirements` の要求を引用付きで 1 件 1 行で並べ、利用者が抜けを確かめられるようにする。続けて Gate、書いた節とテストのファイル、書き込みを確かめた方法と結果、種類別の AC 数、凍結の SHA、試作の patch の path を返し、空でない未決の判断 (既定と行き先を添える)、不足情報、範囲外、未検証、実装が足すテストを 1 件 1 行で並べる。該当の無い種類は書かない。凍結の後の作業も求める依頼では、その報告の先頭に置く。Gate が ready でなければ、凍結していないので計画は実装の入力を満たさないと書く。

## 禁止

- 計画の 4 節以外の行、製品コード、既存の test、設定、外部状態を変えない。足してよいのは受け入れテストと土台のファイルで、変えてよい既存の test は要求が変える規則の基準だけである。作ってよい commit は凍結だけで、push しない。見つけた不足や上流の修正を自分で反映せず、それで Gate を ready にしない。
- 書き込みに失敗しても、別の保存先へ迂回せず、同じ書き込みを再試行しない。
- 資料が決めていない値と未解決の前提を推測で埋めない。既定 (決めない) と行き先 (要求の持ち主) を添えて不足情報にする。計画の決定だけを根拠にした AC を作らない。

## 完了条件

3 段を終えて `check_seal.py seal` が exit 0 で凍結し、`check_seal.py check <repo>` が exit 0 で認めたか、AC が 0 件で凍結しなかったか、3 段目に入る前に Gate を理由に止まった。確かめていない書き込みを成功と報告しない。
