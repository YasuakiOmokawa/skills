## 目的

既存の計画について、何をもって完了とするかを、依頼が求める要求と既存の保証だけに根拠付けた受け入れ基準 (AC) として計画に書き、各 AC を実行できる受け入れテストに翻訳して、後から変えれば git の差分に必ず出る封の commit にする。AC は外から観測できる振る舞いと、コードにあってはならないものだけで書き、計画の決定と実装の選び方を縛らない。

## 原理

- 段の順序: 最初に 3 段の規則をすべて読み、この順に行う。前の段が書いたものを次の段の根拠にする。
  1. 要求と既存の保証: [references/requirements.md](references/requirements.md)
  2. 受け入れ基準と網羅: [references/acceptance-criteria.md](references/acceptance-criteria.md)
  3. 受け入れテストと封: [references/acceptance-tests.md](references/acceptance-tests.md)
- 止めるのは 3 段目だけ: 1〜2 段の未決の判断、不足情報、範囲外、未検証は、その段の節に書いて次の段へ進む。Gate が ready でなければ、受け入れテストを書かず Gate の理由と ready にするための不足条件を報告して止まる。
- 問い返し: 依頼に「問い返し」とあれば [questions.md](references/questions.md) に従う。それ以外では読まない。
- 実行しない確かめ方: DB、コンテナ、サーバの起動、migration、外部への送信が要るコマンドとテストは実行せず、変更前は未実行と書く。

## 契約

- 入力: 書き込み可能な既存の計画と、依頼・計画が名指しする仕様とコード。計画が無いか全体を読めないときは何も書かず、その欠陥を報告する。
- 出力: 計画にそれぞれ唯一の `## Requirements`、`## Ground Review`、`## Acceptance Criteria`、`## MECE Review` と、AC-ID で始まる名前のテストを持つ受け入れテストのファイルと、その 2 つだけを含み `Define-Done-Seal:` の trailer を持つ封の commit。完了は、この skill の `scripts/check_seal.py verify <repo>` の exit 0 で判定する。この skill の起動は、封の commit を作る承認を含む。
- 最終回答: 先頭に `## Requirements` の要求を引用付きで 1 件 1 行で並べ、利用者が抜けを確かめられるようにする。続けて Gate、書いた節とテストのファイル、書き込みを確かめた方法と結果、AC ごとのテスト名、テストを現在のツリーで流したコマンドと結果、封の commit の SHA を返し、`## MECE Review` が要求ごとに判定した対応 (対応あり・欠落・未検証と、根拠のファイルか行)、空でない未決の判断 (既定と行き先を添える)、不足情報、範囲外、未検証を 1 件 1 行で並べる。該当の無い種類は書かない。Gate が ready でなければ、受け入れテストと封を作っていないので計画は実装の入力を満たさないと書く。

## 禁止

- 計画の 4 節以外の行 (状態の行を含む)、製品コード、既存の test、設定、外部状態を変えない。足してよいのは受け入れテストのファイルだけで、作ってよい commit は封の commit だけである。push しない。見つけた不足や上流の修正を計画本文や製品コードへ自分で反映せず、反映したことを理由に Gate を ready にしない。
- 書き込みに失敗しても、別の保存先へ迂回せず、同じ書き込みを再試行しない。内容と計画の状態は回答で返す。
- 資料が決めていない値 (境界点を含む) と未解決の前提を依頼が決めるよう求めても推測で埋めない。その値は既定 (決めない) と行き先 (要求の持ち主) を添えて不足情報にする。計画の決定だけを根拠にした AC とテストを作らない。

## 完了条件

3 段を終えて受け入れテストを現在のツリーで流し、各テストが振る舞いの不在で落ちることを確かめて、封の commit を `scripts/check_seal.py check <repo>` が exit 0 で認めたか、3 段目に入る前に Gate を理由に止まった。再読取などで確かめていない書き込みを成功と報告しない。
