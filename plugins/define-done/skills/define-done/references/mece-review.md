- 追跡してから比べる: 基準に関わるコードは呼ぶ定義まで、共有定義は計画が名指ししないものを含むすべての呼び出し元・利用者まで、リポジトリ内で追い、辿り着いた定義にも同じ追跡を行う。計画が書く状態に別の状態との関係を定める仕様があれば、もう一方の状態を変える既存経路まで、計画が導入する設定値は、それを列挙する運用面 (設定サンプルなど) まで追う。追い終えた範囲を根拠として固定し、名指しされていない運用面は、覆ったと言うときに突き合わせた範囲を示す。
- MECE: 突き合わせるのは次の 3 つだけにし、対応 (ある、無い、矛盾、読めない) と欠落・重複・矛盾を名指しして挙げる。読めない・追えない根拠に依存する比較だけを未検証として範囲を示す。
  - 要求 → 基準: 全 `R-n` が 1 つ以上の基準の出典に挙がっているか。観測できない要求は要求の表に `| R-n | 未検証: <理由> |` と書く。計画が扱わない要求は `| R-n | 範囲外: <理由> |` と書き、計画を直すか利用者がその要求を取り下げるまで進めない。計画が要求を二重に扱う項目は重複として挙げる。
  - 基準 → 出典: 各基準の出典が要求か既存の保証で、基準が出典の範囲を超えないか。根拠が課す義務 (非同期処理の失敗や中断、共有定義の直接の利用者、境界の網羅、待つだけでは示せない不在) から基準へ逆に照合し、計画・基準・要求が扱うと確かめた点 (明示された範囲の宣言、観測の起点、所有する基準) を除いて、欠けだけを具体的に名指しする。経路の完了の証跡と、決定的な失敗シグナルか制御された seam が揃わない不在の主張は、根拠が欠けを支持するときに限り欠落、支持しなければ未検証とする。
  - 決定 → 要求: 計画の決定ごとに、仕える要求を決定の表 `| <決定の ID> | <R-n を ", " 連結> |` に書く。どの要求にも仕えない決定は `| <決定の ID> | 範囲外 |` と書き、範囲外の宣言を上流の修正として求める。要求の外の項目や段階 (後の Stage など) は、範囲外の宣言が計画に無いことを欠落とする。決定からは基準を作らない。
- 根拠: 過去の `## MECE Review` は根拠にしない。
- Gate: 根拠の比較だけから導く。根拠のある欠落・重複・矛盾が残るか、要求の表に範囲外の要求があるか、必要な上流の修正が 1 件でもあるか、必須の比較の根拠が欠けているか、振る舞いを変えない改修の目的を `[禁止]` の基準で書けていないときは ready にせず、理由を書く。それ以外は ready とする。
- 書く節: 計画の唯一の `## MECE Review` 節 (無ければ `## Acceptance Criteria` 節の直後に挿入) を、現在の AC-ID の集合を書く `- AC IDs:` 行と、`- Gate: ready` または ready 以外の値と理由を書く `- Gate:` 行 (各一つ)、`###` 以下の見出しのレビュー本文で置き換える。`- Fingerprint:` 行は検証の対応付けの段の script が書く。本文は要求の表、決定の表、指摘、必要な上流の修正を、確認済みの結果と未検証の範囲に分けて書き、本文の箇条を `- AC-` で始めない。
