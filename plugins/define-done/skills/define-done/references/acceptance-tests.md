# 受け入れテスト

- 段の目的: 各 AC を、実行できる受け入れテストに翻訳する。テストがそのまま oracle であり、散文の oracle や検証の対応付けを別に書かない。
- 手本: 受け入れテストは、repo の既存のテストと見分けがつかない形で書く。手本は、repo の文書 (CLAUDE.md、AGENTS.md、テストの指針) が決めるテストの書き方と、AC が観測する外の境界を通る既存のテストである。依頼か計画が置き場所やランナーを名指ししていれば、そこにあるテストを手本にする。実装の選択を固定する既存の試験 (内部の message や関数を語彙にする部品のテストなど) は手本にしない。
  - 手本から取るもの: 置き場所、ファイル名の形、テストの構造、ランナーとその設定、補助 (helper、fixture、factory、差し替え口)、外の境界の通り方 (プロセス内で呼ぶ、サーバを起動して開く、など)、共有する状態の扱い。
  - 書く先: AC の機能を扱う手本のファイルがあれば、そのファイルにテストを足す。無ければ、手本と同じ置き場所に、手本と同じ名前の形で新しいファイルを書く。ファイル名は repo の機能の語で付け、issue の番号や計画の名前を入れない。
  - 補助: 既存の補助を使う。足りない分は、既存の補助のファイルに足す。
  - 既存の行: 既存のテストと補助には足すだけにし、既存の行はそのまま残す (import の行に名前を足すことは数えない)。要求が既存のテストの固定する振る舞いを変えるときだけ、そのテストを書き直し、ファイルとテスト名と根拠の `R-n` を `## MECE Review` に書く。
  - 足さないもの: ディレクトリ、ランナーの設定、依存。新しいディレクトリを作ってよいのは、repo の規則 (テストが製品コードの構造を写す、など) が求めるときと、依頼が名指しした置き場所が無いときだけである。
  - 手本が無いとき: AC が観測する外の境界を通る既存のテストが repo に無ければ、その AC のテストを書かず、観測の手段を添えて回答の未検証に並べる。repo にテストの置き場所が 1 つも無く、依頼も名指ししていなければ、どの AC のテストも書かず、不足情報として返す。
- AC とテストの対応: 各 AC に 1 つ以上のテストを書き、新しく書くテストはどれも AC に対応させる。テスト名は観測する振る舞いを業務の言葉で書き、AC-ID や計画の語をコードに書かない。AC とテストの対応は `check` に渡す。実画面、CI、deploy の後でしか観測できない AC と、作れない部品 (入っていない依存、起動できない DB など) が要る AC はテストを書かず、観測の手段を添えて回答の未検証に並べる。
- 決定論: 時刻、乱数、外部への送信は、手本が使う seam か仕様が名指しした seam で固定する。時間で変わる表示は時計を止め、通信の応答を待ってから進める。実時間の待機と実行順への依存を書かない。手本が共有している状態 (サーバ、seed、プロセスの中の store、試行の計数、一時ファイル) は手本と同じ扱いで使い、受け入れテストが変えた分は各テストの後に戻す。repo の test command が複数のファイルを 1 つのプロセスで流すなら、残った状態は既存のテストを落とす。自動で待つ assert で不在を確かめない (待つ間にタイマーが消して通る)。seam が無くて固定できない基準は、テストを書かずに不足情報として返す。
- 期待値: 要求の原文の値か、そこから計算したリテラルだけを使う。資料が決めていない値 (境界ちょうどの扱い、上限など) をテストに書かない。
- 実行環境: テストが実行環境の機能 (暗号の方式、API の版など) に頼るときは、repo の CI が固定する実行環境の版 (workflow の pin など) でも使えることを確かめ、使えなければその機能に頼らない形にするか不足情報にする。
- 変更前の tree に無い module: 試作の実装を渡さずに確かめるときは、変更前の tree に無い module をテストが実行時に import する (静的に import すると変更前の tree でテストが実行されず、落ちたものと数えられない)。

## `check` に渡す JSON

`{"test_command": "<受け入れテストを書いたファイルを手本のランナーで流し、結果を {report} の path に JUnit XML か RSpec の JSON で書くコマンド>", "files": [<受け入れテストを書いたファイル、足した補助と期待値のファイル、repo の中にあれば計画>], "tests": [{"ac": "AC-001", "file": "<テストのファイル>", "name": "<テスト名>"}]}` に、次を足す。テスト名は describe の名前を付けずに書く。

- `"plan": "<計画の path>"`: 計画が repo の外にあれば渡す。
- `"spike": "<試作の実装の patch の path>"`: `spike-close` が出した path を渡す。
- `"check_command": "<repo の lint、型検査、dead code の検査を流すコマンド>"`: テストを含まないコマンドを渡す。
- `"rewrites": [{"file": "<書き直した既存のテストのファイル>", "reason": "<変わる振る舞いと根拠の R-n>"}]`: 既存の行を変えたファイルごとに渡す。
- `"new_dirs": [{"path": "<新しく作ったディレクトリ>", "reason": "<それを求める repo の規則か、依頼の名指しの引用>"}]`: 新しく作ったディレクトリごとに渡す。
- `"implemented": ["AC-NNN"]`: 実装がすでに HEAD に入っていて、変更前の tree で落ちることを確かめられない `[規則]` の基準を挙げる。

`{report}` は repo の root からの相対の path に置き換わり、コマンドは repo の root で流れるので、コンテナの中で流すランナーにもそのまま渡せる。ビルドが要るテストはビルドも、DB やサーバが要るテストは repo が示す起動もコマンドの前に済ませる。

## `check` が確かめること

`check` は commit を作らず、exit 0 か、理由を出して exit 1 を返す。

- 計画: Gate が ready であること、`- AC IDs:` の行が基準の AC-ID と一致すること、テストを対応させた AC が計画にあり種類の印と出典を持つこと、基準の出典の `R-n` が要求にあること、要求の表の各行が、その要求を出典に挙げる AC-ID か `未検証:`・`範囲外:`・`不足情報:` で始まること、要求の行が検査コマンドの通過だけや今回は作らないものを述べていないこと。`spike-open` に計画を渡していれば、その時点から計画の 4 節の外が変わっていないことも確かめる。
- 既存のテスト: 渡したファイルの置き場所が HEAD にあること、HEAD にあるファイルへの変更が行の追加だけであること (import と require の行は数えない)、足した行に AC-ID が無いこと。`rewrites` と `new_dirs` に挙げたものは通し、`report` が最終回答に並べる。
- 種類: 今の tree で、対応に挙げたテストだけを数え、`[規則]` が落ち `[非影響]` が通ること (同じファイルの既存のテストは数えない)。新しいファイルに AC の無いテストがあれば拒む。`[規則]` のテストが今の tree で読み込めずに実行されなかったときは、実装のある tree (試作の実装を当てた tree。試作を渡さなければ、退避する前の作業ツリー) でそのテストが通っていれば、落ちたものと数える。`[非影響]` のテストと skip されたテストは、実行されなければ拒む。
- 試作の実装: 試作の実装を当てた tree で `[規則]` と `[非影響]` のテストが通ることと `check_command` が通ることを確かめ、外す。
- 退避: 渡したファイルの外の変更 (実装の途中の変更を含む) を自分で退避して HEAD の製品コードで流し、終わったら戻す。戻せなかったときは退避を stash に残し、戻すコマンドを出すので、そのとおりに戻す。

## 手順

受け入れテストを書いたら、この順に進める。AC が 0 件ならテストを書かない。repo でなければ `check` を流せないので、書いたものを残し、確かめていないと報告する。

1. 全体を流す: `check` の前に repo の test command 全体を 1 回流し、受け入れテストを足して新しく落ちたテストが規則の基準のテストだけであることを確かめる。ほかのテストが落ちたら、受け入れテストか足した補助を直す。全体を流せない (起動できないサービスが要る、など) ときは、流せなかったことを回答の未検証に書く。
2. 試作の実装を書く: 試作の実装は計画どおりの最小の実装で、`check_done.py spike-open <repo> <計画の path> <受け入れテストを書いたファイルと足した補助>...` が作る一時的な複製の中で書く (HEAD の複製に依存の dir を link し、渡したファイルを写して、その path を出す。skill の起動がこの複製と patch の作成を承認する)。作業ツリーの製品コードには書かない。複製の中でテストを流すときの env の file は、runner の flag で repo の file を指す。受け入れテストは repo で直し、複製へ写し直す。決定どおりの形を repo の検査が拒んだら、Gate の規則の「検査が拒んだ決定」で扱いを決める (計画の 4 節の外は直さない)。計画が実装を決めきらず試作の実装を書けないときだけ試作を省き、回答の未検証に書く。
3. 試作を閉じる: 書き終えたら `check_done.py spike-close <repo> <複製の path>` が差分を repo の外の patch に出して複製を消す (実装はこの patch を当てて始めてよい)。
4. 確かめる: この skill の `scripts/check_done.py check <repo>` を流し、標準入力に上の JSON を渡す。exit 1 なら出た理由を直して流し直す。試作の実装を当てた tree でテストが通らなければ、テストか要求が誤っているので、直すか衝突として報告する。落ちる理由が振る舞いの不在 (未実装の例外、期待値の不一致) であることを出力で確かめる。
5. 最終回答を返す: `check_done.py report <repo> [計画の path]` の出力を写して書く。依頼が受け入れテストの後の作業 (実装など) まで求めているなら、その作業を終えてから `report` を流し、最後の報告の先頭に、要求を省かず引用ごと写して置く。未検証は、同じ事柄を指す行を 1 行にまとめ、後の作業で確かめたものには確かめた方法と結果を添える。

## 後から直すとき

- 受け入れテストか計画を直したとき: `check` を流し直す。
- 要求が変わったとき: 計画の 4 節と受け入れテストを直して `check` を流し直す。変えた要求は利用者の発言を引用し、`<場所>` を `依頼` にする。意味の変わらない要求と基準は番号を保ち、意味の変わった基準は新しい AC-ID にする。変えた要求が正本 (issue など) と食い違うなら、正本の更新を `### 未決の判断` に書く。
