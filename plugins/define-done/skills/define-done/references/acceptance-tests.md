# 受け入れテストと封

- 段の目的: 各 AC を、実行できる受け入れテストに翻訳する。テストがそのまま oracle であり、散文の oracle や検証の対応付けを別に書かない。
- 置き場所とランナー: 依頼か計画が名指しする置き場所とランナーを使い、無ければ repo の既存のテストの置き場所と test command に合わせる。新しい依存を足さない。`[規則]` と `[非影響]` は別のファイルに書き、1 つのファイルには 1 つの種類だけを置く。期待値のファイル (golden など) は、それを読むテストの種類に付ける。
- AC とテストの対応: 各 AC に 1 つ以上のテストを書き、どの AC にも対応しないテストを書かない。テスト名は観測する振る舞いを業務の言葉で書き、AC-ID や計画の語をテストと土台のコードに書かない。AC とテストの対応は `seal` に渡し、封が記録する。実画面、CI、deploy の後でしか観測できない AC と、作れない部品 (入っていない依存、起動できない DB など) が要る AC はテストを書かず、`verify` の判定に入らないので、観測の手段を添えて回答の未検証に並べる。
- 土台: 受け入れテストが import や require してよいのは、置き場所の直下の `harness/` (土台) とテストランナーだけで、`seal` と `check` が検査する。内部に触れてよいのは土台だけで、触れてよい内部は実行時の入口 (実行の設定が指す entry、package の bin、ビルドの出力、`rails_helper` が読むアプリ) と、既存の試験が使っている差し替え口 (時計、送信先、factory など) に限る。それ以外の内部が要る AC はテストを書かず、未検証か不足情報にする。土台が無いか足りなければ、書いた AC に要る部品だけを足す。Ruby の require の検査は定数の参照を見ないので、テストは内部の定数に触れず土台を通す。
- 外の境界の通り方: HTTP はアプリの入口をプロセス内で呼ぶ (request spec を含む)。画面は、repo に実ブラウザのランナー (Playwright など) があれば、ビルドした画面を実ブラウザで開き、通信の契約、認証ライブラリの公開 API、ブラウザの API (クリップボード、時計) だけを差し替える。部品のテストハーネス (Foldkit の Scene など) は内部の語彙を固定するので使わない。コマンドは実行して出力と終了コードを見る。
- 決定論: 時刻、乱数、外部への送信は仕様が名指しした seam (注入する時計、差し替える送信先など) で固定する。時間で変わる表示は時計を止め、通信の応答を待ってから進める。実時間の待機、テスト間で共有する状態、実行順への依存を書かない。土台が動かした、受け入れテストの外と共有する状態 (プロセスの中の store、試行の計数、一時ファイル) は各テストの後に戻す。repo の test command が複数のファイルを 1 つのプロセスで流すなら、残った状態は既存のテストを落とす。自動で待つ assert で不在を確かめない (待つ間にタイマーが消して通る)。seam が無くて固定できない基準は、テストを書かずに不足情報として返す。
- 期待値: 要求の原文の値か、そこから計算したリテラルだけを使う。資料が決めていない値 (境界ちょうどの扱い、上限など) をテストに書かない。
- 封: 書いたら、この skill の `scripts/check_seal.py seal <repo>` を流し、標準入力に JSON `{"test_command": "<受け入れテストだけを流し、結果を {report} の path に JUnit XML か RSpec の JSON で書くコマンド>", "rule": [<[規則] のファイル>], "non_impact": [<[非影響] のファイル、土台、repo の中にあれば計画>], "subject": "test: <計画のファイル名> の受け入れテスト"}` を渡し、JSON の `"tests"` に AC ごとのテストを `[{"ac": "AC-001", "file": "<テストのファイル>", "name": "<テスト名>"}]` の形で並べる。`{report}` は repo の root からの相対の path に置き換わり、コマンドは repo の root で流れるので、コンテナの中で流すランナーにもそのまま渡せる。ビルドが要るテストはビルドも、DB が要るテストは repo が示す DB の起動もコマンドの前に済ませる。`seal` の前に repo の test command 全体を 1 回流し、受け入れテストを足して新しく落ちたテストが規則の基準のテストだけであることを確かめる。ほかのテストが落ちたら土台を直す。全体を流せない (起動できないサービスが要る、など) ときは、流せなかったことを回答の未検証に書く。`seal` は今の tree でテストを流し、`[規則]` が落ち `[非影響]` が通るときだけ、ファイル、種類、AC とテストの対応を trailer に記録した封の commit を作る。食い違い、実行されなかったテスト (テスト名の対応の誤り、import やセットアップの失敗)、AC の無いテスト、コードの中の AC-ID、土台の外の import があれば exit 1 で封を作らないので、直して流し直す。封の後に受け入れテスト、土台、計画を直したときも、同じ JSON で `seal` を流し直す。`seal` は変わったファイルだけを新しい封に記録する。実装の変更が tree にあると規則の基準のテストが通って `seal` が拒むので、実装の変更を退避 (`git stash` など) してから流し、封の後に戻す。`verify` は封が記録した結果を信じ、今の tree だけを流す。落ちる理由が振る舞いの不在 (未実装の例外、期待値の不一致) であることを出力で確かめる。現在のツリーが計画の変更をすでに含むなら、変更後に確かめたと回答に書く。
  - 要求が既存の `[規則]` の振る舞いを変えるときだけ、そのテストを書き直して同じ封に含め、JSON に `"supersedes": "<置き換える AC-ID> (<R-n>)"` を足す。恒久に守っている規則のファイルを `supersedes` 無しで含めると `seal` が拒む。置き換える基準が旧い形式の封 (trailer に `Define-Done-Files` の無い封) のテストにあり、その封が既定の branch から辿れるときは、そのファイルの保護は解けている。封に含めず、置き換える AC-ID を `## MECE Review` に書き、書き換えは実装に任せる。それ以外の既存のテストは変えない。
  - AC が 0 件なら封を作らない。封の後、`check_seal.py check <repo>` が exit 0 を返すことを確かめ、SHA を回答で返す。repo でないか封を作れなかったら、書いたものを残し、封が無いので実装の入力を満たさないと報告する。push しない。
