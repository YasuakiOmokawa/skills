- 段の目的: 各 AC を、実行できる受け入れテストに翻訳する。テストがそのまま oracle であり、散文の oracle や検証の対応付けを別に書かない。
- 置き場所とランナー: 依頼か計画が名指しする置き場所とランナーを使い、無ければ repo の既存のテストの置き場所と test command に合わせる。新しい依存を足さない。
- AC とテストの対応: 各 AC に 1 つ以上のテストを書き、テスト名を AC-ID で始める。どの AC にも対応しないテストを書かない。実画面、CI や deploy の後でしか観測できない AC はテストを書かず、`verify` の判定に入らないので、観測の手段を添えて回答の未検証に並べる。
- 外の境界だけを通す: テストが呼ぶのは、AC の規則の書いてよい名前 (仕様が名指しした interface、既存の試験の seam) だけにする。計画が新しく作る内部の関数やファイルを import しない。
- 決定論: 時刻、乱数、外部への送信は仕様が名指しした seam (注入する時計、差し替える送信先など) で固定する。実時間の待機、テスト間で共有する状態、実行順への依存を書かない。seam が無くて固定できない基準は、テストを書かずに不足情報として返す。
- 期待値: 要求の原文の値か、そこから計算したリテラルだけを使う。資料が決めていない値 (境界ちょうどの扱い、上限など) をテストに書かない。
- `[禁止]`: あってはならない文字列の pattern を、正の pathspec で絞った走査範囲に `git grep -n -E` で当て、0 件を期待するテストにする。
- red を確かめる: 書いた後、現在のツリーでテストを流し、各テストが振る舞いの不在 (未実装の例外、期待値の不一致) で落ちることを確かめる。import、構文、セットアップの失敗は red に数えず、テストを直して流し直す。変更前から通るテストは、非影響の基準なら残し、それ以外は書き直す。DB、コンテナ、サーバの起動、外部への送信が要るテストは流さず、未実行と報告する。
- 書き込み: テストのファイルは Write か Edit で書き、再読取で確かめる。
- 封: red を確かめた後、受け入れテストのファイルと、repo の中にあれば計画のファイルだけを pathspec で指定して 1 つの commit にする。index にある他の変更は含めない。message は 1 行目を `test: <計画のファイル名> の受け入れテスト` とし、末尾に trailer `Define-Done-Seal: <AC-ID を昇順で ", " 連結>` と `Define-Done-Test-Command: <受け入れテストだけを流すコマンド>` を置き、他の trailer (共著者など) を付けない。commit の後、含まれたファイルを `git show` で確かめ、SHA を回答で返す。repo でないか commit に失敗したら、書いたものを残し、封が無いので実装の入力を満たさないと報告する。push しない。
