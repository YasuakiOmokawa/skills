# 受け入れテストと凍結

- 段の目的: 各 AC を、実行できる受け入れテストに翻訳する。テストがそのまま oracle であり、散文の oracle や検証の対応付けを別に書かない。
- 置き場所とランナー: 依頼か計画が名指しする置き場所とランナーを使い、無ければ repo の既存のテストの置き場所と test command に合わせる。新しい依存を足さない。`[規則]` と `[非影響]` は別のファイルに書き、1 つのファイルには 1 つの種類だけを置く。期待値のファイル (golden など) は、それを読むテストの種類に付ける。
- AC とテストの対応: 各 AC に 1 つ以上のテストを書き、どの AC にも対応しないテストを書かない。テスト名は観測する振る舞いを業務の言葉で書き、AC-ID や計画の語をテストと土台のコードに書かない。AC とテストの対応は `seal` に渡し、凍結の commit が記録する。実画面、CI、deploy の後でしか観測できない AC と、作れない部品 (入っていない依存、起動できない DB など) が要る AC はテストを書かず、`verify` の判定に入らないので、観測の手段を添えて回答の未検証に並べる。
- 土台: 受け入れテストが import や require してよいのは、置き場所の直下の `harness/` (土台) とテストランナーだけで、`seal` と `check` が検査する。内部に触れてよいのは土台だけで、触れてよい内部は実行時の入口 (実行の設定が指す entry、package の bin、ビルドの出力、`rails_helper` が読むアプリ) と、既存の試験が使っている差し替え口 (時計、送信先、factory など) に限る。それ以外の内部が要る AC はテストを書かず、未検証か不足情報にする。土台が無いか足りなければ、書いた AC に要る部品だけを足す。土台が実行環境の機能 (暗号の方式、API の版など) に頼るときは、repo の CI が固定する実行環境の版 (workflow の pin など) でも使えることを確かめ、使えなければその機能に頼らない形にするか不足情報にする。Ruby の require の検査は定数の参照を見ないので、テストは内部の定数に触れず土台を通す。試作の実装を渡さない最初の凍結では、変更前の tree に無い module を土台が実行時に import する (静的に import すると変更前の tree でテストが実行されず、通る tree も無いので、落ちたものと数えられない)。
- 外の境界の通り方: HTTP はアプリの入口をプロセス内で呼ぶ (request spec を含む)。画面は、repo に実ブラウザのランナー (Playwright など) があれば、ビルドした画面を実ブラウザで開き、通信の契約、認証ライブラリの公開 API、ブラウザの API (クリップボード、時計) だけを差し替える。部品のテストハーネス (Foldkit の Scene など) は内部の語彙を固定するので使わない。コマンドは実行して出力と終了コードを見る。
- 決定論: 時刻、乱数、外部への送信は仕様が名指しした seam (注入する時計、差し替える送信先など) で固定する。時間で変わる表示は時計を止め、通信の応答を待ってから進める。実時間の待機、テスト間で共有する状態、実行順への依存を書かない。土台が動かした、受け入れテストの外と共有する状態 (プロセスの中の store、試行の計数、一時ファイル) は各テストの後に戻す。repo の test command が複数のファイルを 1 つのプロセスで流すなら、残った状態は既存のテストを落とす。自動で待つ assert で不在を確かめない (待つ間にタイマーが消して通る)。seam が無くて固定できない基準は、テストを書かずに不足情報として返す。
- 期待値: 要求の原文の値か、そこから計算したリテラルだけを使う。資料が決めていない値 (境界ちょうどの扱い、上限など) をテストに書かない。

## `seal` に渡す JSON

`{"test_command": "<受け入れテストだけを流し、結果を {report} の path に JUnit XML か RSpec の JSON で書くコマンド>", "rule": [<[規則] のファイル>], "non_impact": [<[非影響] のファイル、土台、repo の中にあれば計画>]}` に、次を足す。

- `"tests"`: AC ごとのテストを `[{"ac": "AC-001", "file": "<テストのファイル>", "name": "<テスト名>"}]` の形で並べる。テスト名は describe の名前を付けずに書く。
- `"plan": "<計画の path>"`: 計画が repo の外にあれば渡す。commit の subject は `seal` が計画の path から作る。`seal` が path を覚えるので、`reseal` と `report` には渡さなくてよい。
- `"spike": "<試作の実装の patch の path>"`: `spike-close` が出した path を渡す。
- `"check_command": "<repo の lint、型検査、dead code の検査を流すコマンド>"`: `spike` が無ければ封の tree で流れるので、テストを含まないコマンドを渡す。
- `"supersedes": "<置き換える AC-ID> (<R-n>)"`: 要求が既存の `[規則]` の振る舞いを変えるときだけ、そのテストを書き直して同じ凍結に含め、これを足す。恒久に守っている規則のファイルを `supersedes` 無しで含めると `seal` が拒む。置き換える基準が旧い形式の凍結の commit (trailer に `Define-Done-Files` の無い凍結) のテストにあり、その凍結の commit が既定の branch から辿れるときは、そのファイルの保護は解けている。凍結に含めず、置き換える AC-ID を `## MECE Review` に書き、書き換えは実装に任せる。それ以外の既存のテストは変えない。ファイルごとの保護の状態は `check_seal.py check <repo> <ファイル>...` が出す (凍結の前でも使える)。

`{report}` は repo の root からの相対の path に置き換わり、コマンドは repo の root で流れるので、コンテナの中で流すランナーにもそのまま渡せる。ビルドが要るテストはビルドも、DB が要るテストは repo が示す DB の起動もコマンドの前に済ませる。

## `seal` が確かめること

- 計画: 流す前に計画を読み、Gate が ready であること、`- AC IDs:` の行が基準の AC-ID と一致すること、テストを対応させた AC が計画にあり種類がファイルと合うこと、基準の出典の `R-n` が要求にあること、要求の表の各行が、その要求を出典に挙げる AC-ID か `未検証:`・`範囲外:`・`不足情報:` で始まること、要求の行が検査コマンドの通過だけや今回は作らないものを述べていないことを照合し、渡したファイルのほかの凍結済みのファイルに未 commit の変更が無いことも確かめる。`spike-open` に計画を渡していれば、その時点から計画の 4 節の外が変わっていないことも確かめる。
- 試作の実装: 試作の実装を当てた tree で `[規則]` と `[非影響]` のテストが通ることと `check_command` が通ることを確かめ、外してから凍結する。
- 今の tree: 今の tree でテストを流し、`[規則]` が落ち `[非影響]` が通るときだけ、ファイル、種類、AC とテストの対応を trailer に記録した凍結の commit を作る。`[規則]` のテストが今の tree で読み込めずに実行されなかったときは、実装のある tree (試作の実装を当てた tree。試作を渡さなければ、退避する前の作業ツリー) でそのテストが通っていれば、落ちたものと数える。`[非影響]` のテストと skip されたテストは、実行されなければ拒む。
- 凍結しない場合: 計画の食い違い、凍結済みのファイルの変更、種類の食い違い、実行されなかったテスト (テスト名の対応の誤り、import やセットアップの失敗)、AC の無いテスト、コードの中の AC-ID、土台の外の import があれば exit 1 で凍結しない。
- 退避: `seal` は渡したファイルの外の変更 (実装の途中の変更を含む) を自分で退避して HEAD の製品コードで流し、終わったら戻す。戻せなかったときは退避を stash に残し、戻すコマンドを出すので、そのとおりに戻す。`seal` は変わったファイルだけを新しい凍結の commit に記録する。

## 凍結した後に使う command

- 直したとき: 凍結の後に受け入れテスト、土台、計画を直したときは、`check_seal.py reseal <repo>` を流し直す。`reseal` は直前の凍結の commit の trailer から JSON を組み立て、標準入力の JSON (足す `tests`、`spike`、`check_command`、`reworded`) で上書きする。`tests` に渡した AC とファイルの組は、その組のテストが渡したものに置き換わるので、テスト名を変えたら、その組のテストをすべて渡す。計画の `## Acceptance Criteria` から消えた基準は、`reseal` がテストの対応を外し、外した AC-ID を出す。
- 要求が変わったとき: 凍結の後に利用者が要求を変えたら、計画の 4 節、受け入れテスト、土台を直して `reseal` する。変えた要求は利用者の発言を引用し、`<場所>` を `依頼` にする。意味の変わらない要求と基準は番号を保ち、意味の変わった基準は新しい AC-ID にする。`seal` と `reseal` は同じ計画の前の凍結と照合し、同じ AC-ID で本文の変わった基準と、同じ文で番号だけが変わった基準と要求を拒む。言い回しだけを直した基準は `"reworded": ["AC-NNN"]` に挙げる (凍結の commit に残る)。変えた要求が正本 (issue など) と食い違うなら、正本の更新を `### 未決の判断` に書く。
- 完了の判定: `verify` は凍結の commit が記録した結果を信じ、今の tree だけを流す。
- 最終回答の材料: `check_seal.py report <repo>` が、計画と凍結の commit から、引用付きの要求、Gate、種類別の AC 数、凍結の SHA、凍結したファイル、試作の patch の path、基準の無い要求、実装が足すテスト、未決の判断、未検証、検査が拒んだ決定を抜き出す。

## 凍結の手順

受け入れテストと土台を書いたら、この順に進める。AC が 0 件なら凍結しない。repo でないか凍結できなかったら、書いたものを残し、凍結の commit が無いので実装の入力を満たさないと報告する。push しない。

1. 全体を流す: `seal` の前に repo の test command 全体を 1 回流し、受け入れテストを足して新しく落ちたテストが規則の基準のテストだけであることを確かめる。ほかのテストが落ちたら土台を直す。全体を流せない (起動できないサービスが要る、など) ときは、流せなかったことを回答の未検証に書く。
2. 試作の実装を書く: 試作の実装は計画どおりの最小の実装で、`check_seal.py spike-open <repo> <計画の path> <受け入れテストと土台のファイル>...` が作る一時的な複製の中で書く (HEAD の複製に依存の dir を link し、渡したファイルを写して、その path を出す。skill の起動がこの複製と patch の作成を承認する)。作業ツリーの製品コードには書かない。複製の中でテストを流すときの env の file は、runner の flag で repo の file を指す。受け入れテストと土台は repo で直し、複製へ写し直す。決定どおりの形を repo の検査が拒んだら、Gate の規則の「検査が拒んだ決定」で扱いを決める (計画の 4 節の外は直さない)。計画が実装を決めきらず試作の実装を書けないときだけ試作を省き、回答の未検証に書く。
3. 試作を閉じる: 書き終えたら `check_seal.py spike-close <repo> <複製の path>` が差分を repo の外の patch に出して複製を消す (実装はこの patch を当てて始めてよい)。
4. 凍結する: この skill の `scripts/check_seal.py seal <repo>` を流し、標準入力に上の JSON を渡す。exit 1 なら凍結していないので、出た理由を直して流し直す。試作の実装を当てた tree でテストが通らなければ、テスト、土台、要求のどれかが誤っているので、直すか衝突として報告する。落ちる理由が振る舞いの不在 (未実装の例外、期待値の不一致) であることを出力で確かめる。現在のツリーが計画の変更をすでに含むなら、変更後に確かめたと回答に書く。
5. 確かめる: 凍結の後、`check_seal.py check <repo>` が exit 0 を返すことを確かめる。
6. 最終回答を返す: `check_seal.py report` の出力を写して書く。依頼が凍結の後の作業 (実装など) まで求めているなら、その作業を終えてから `report` を流し、最後の報告の先頭に、要求を省かず引用ごと写して置く。未検証は、同じ事柄を指す行を 1 行にまとめ、凍結の後の作業で確かめたものには確かめた方法と結果を添える。
