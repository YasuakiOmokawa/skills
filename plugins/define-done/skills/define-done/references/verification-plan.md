- oracle による受け入れ判定: oracle は AC から導く。`[振る舞い]` の oracle は外の境界を通した観測で書き、`[禁止]` の oracle は定型 `check_plan.py の禁止の検査が通り、Violation sample を入れると落ち、除くと通る` だけを書き、検索のコマンドを書かない。観測の起点 (Evidence anchors) には、リポジトリに実在すると確かめた外の境界と既存の試験の seam (ファイル、関数、テスト、コマンド) だけを書く。リポジトリ外の依存は anchor を創作せず Prerequisites に未解決として残す。Oracle が名指しするファイルも受け入れ基準の規則の書いてよい名前に限り、計画が新しく作る内部のファイルや試験は観測する振る舞いで書く。
- 禁止の行: `[禁止]` のエントリは、禁じたものを探す pattern と走査範囲を `- Forbidden row: {"pattern": "<git grep -E の pattern>", "pathspec": ["<pathspec>", ...]}` の 1 行の JSON で書く。key はこの 2 つだけにし、走査範囲は正の pathspec で絞り、除外 (`:!`、`:^`、`:(exclude)`) を書かない。禁止の行は計画の中にだけ置き、対象の repo に禁止の表や検査のファイルを足さない。文字列の pattern で書けない禁止 (import の形、型の形など) は `[禁止]` にせず、repo に検出する lint の規則があれば `[振る舞い]` 「repo の lint が exit 0 で終わる」の観測に含め、無ければ不足情報として返す。
- 違反の見本: `[禁止]` のエントリは禁じたものを含む最小の例を `- Violation sample:` に「`<repo からの相対 path>` に `<1 行の内容>`」の形で 1 行に書く。path が新しいファイルなら script が作って消し、既存のファイルなら末尾に足して元に戻す。見本は禁じたものそのものにし、代わりの文字列にしない。1 行で書けなければ見本を分けるか基準を分ける。
- 否定の主張には決定的な証跡を求める: 不在、件数の上限、並行性、経過時間、非影響に基づく oracle は、経路と観測境界が完了した肯定的証跡と、決定的な失敗シグナルまたは制御された seam を Required effects が名指ししたときだけ、対応付けを完了とする。固定時間の待機だけなら、足りない証跡を Prerequisites に未解決として残す。列挙した書き込み経路で確かめる不変条件は、関係するいずれかの状態の書き手が列挙の外に現れたら決定的に落ちる tripwire を Required effects が名指ししたときだけ完了とする。経路ごとの確認だけなら、tripwire の不足を Prerequisites に未解決として残す。`[禁止]` では、禁止の行と `- Violation sample:` がこの失敗シグナルを担う。
- 観測できない場所: CI や deploy の後でしか観測できない `[振る舞い]` は、その実行を Prerequisites に書き、構造の確認 (workflow の定義を読む、など) で代用しない。
- 書く節: 計画の唯一の `## Verification Plan` 節の内容全体を置き換える。節は `- AC IDs: <現在の AC-ID を昇順で ", " 連結>` 行と、AC ごとに 1 つの `### AC-NNN` エントリだけから成り、各エントリは空でない `- Oracle:`、`- Evidence anchors:`、`- Prerequisites:`、`- Required effects:` を 1 行ずつ持ち、`[禁止]` のエントリはさらに `- Violation sample:` と `- Forbidden row:` を 1 行ずつ持つ。検証の意図はこの節にだけ置き、別の検証文書を作らない。前提が未解決でも、Required effects には oracle の観測に要る最小限の具体的な操作や状態変化を書く。これは後で要る承認の記述であって、承認を与えるものではない。観測に操作も状態変化も要らなければ `無い` と書く。`- Violation sample:` の一時的な出し入れは検証の一部で承認を要しないので、Required effects に書かない。
- 名前の照合: 節を書いた後、計画の実装案の節 (決定、作るもの、変更対象、順序など) に backtick で書かれた識別子とパスを抜き出し、`## Acceptance Criteria` と `## Verification Plan` の両節に対して `grep -nF` で照合する。当たった名前は受け入れ基準の規則の書いてよい名前 (外の境界、仕様の節が名指しした名前、判断の正本が名指しした外の境界、既存の試験の seam、文書の置き場所、`[禁止]` が禁じる対象) のどれかなら残し、それ以外 (計画が新しく作る内部の名前、判断の正本が名指しした内部の関数名を含む) を含む基準とエントリは書き直す。書き直したら照合をやり直し、当たりが残らなくなってから封をする。
- 封: 節を書いて再読取で確かめ、名前の照合を終えた後、この skill の dir の `scripts/check_plan.py` を `python3 <script> seal <計画> <対象の repo>` で流す。exit 0 なら script が `## MECE Review` に `- Fingerprint:` 行を書く。exit 1 なら出力の 1 行ごとに該当する節を直して流し直す。計画を直すか利用者が決めるまで直せないもの (範囲外の要求など) は、Gate を ready でない値に戻し、出力を報告する。封の後は `## Requirements`、`## Acceptance Criteria`、`## Verification Plan` を変えない。
