# 受け入れ基準と網羅

## 受け入れ基準 (`## Acceptance Criteria`)

- YAGNI: 要求が求める範囲の振る舞いだけを基準にし、その観測方法を定める計画内の記述 (`## Ground Review` を含むレビュー指摘) は、書いてよい名前の範囲で基準に反映する。範囲を超える新しい振る舞いの推奨や別チケットの項目は範囲外として返す。資料が決めていない値は基準にせず、決まっている条件だけを基準にする。要求の条件を満たさない入力 (条件の外側) は、決めていない値に当たらない。
- 基準は 2 種類だけ: 実装はこの 2 種類を満たす範囲で自由に選べるものとし、基準は実装の選び方を縛らない。
  - `[振る舞い]`: 一つの前提または操作と、外の呼び出し側から観測できる一つの結果の対。外とはリポジトリのコードの外にいる主体 (利用者、他のサービス、CI、運用者、文書の読み手) で、仕様の節が名指しした interface と、既存の試験が固定している既存の interface も外の境界に含める。ただし、どの実装・部品・runtime・library・file が担うか (実装の選択) を返す関数と、その戻り値を固定する試験は含めない。観測するのは描画された内容、応答、保存された値などの結果である。リポジトリの中で export された関数は、ここに挙げたもの以外は外に含めない。境界は interface であり、動いている環境でなくてよい (HTTP の handler をプロセス内で呼ぶ、など)。実行時に起きてはならないこと (送らない、書き換えない) も、失敗か非影響の `[振る舞い]` にする。
  - `[禁止]`: コードに静的にあってはならないもの (秘密の混入、値の写し、禁じられた依存や直接の利用、旧名の残存) で、静的な検査か外部状態に触れない単体試験で検出できるもの。e2e や DB が要る試験でしか検出できないものは `[振る舞い]` にする。
  - どちらにも当たらないもの (計画が作る関数やファイルの名前、内部の呼び出し関係や包み方、実装の手順) は基準にしない。振る舞いの代わりに置かれた禁止 (「このファイルを変えない」など) は、守りたい振る舞いが変わらない非影響の `[振る舞い]` に書き直す。生成物 (bundle、build の出力) の中身も、要求が中身そのものを禁じるとき (秘密を含めない、など) だけ基準にし、振る舞い (route が応答しない、など) を確かめる代わりに使わない。
- 出典: 各基準は出典を持ち、出典にできるのは `## Requirements` の要求 (`R-n`) と、変更前の repo に既にある試験・guard (製品コードの中で入力を拒む検査を含む)・不変条件を述べる文書のパス (既存の保証) だけである。実装の選択を固定する試験は既存の保証にしない。計画の決定 (選んだ手順・値・仕組み、`D` と数字の ID)、作るもの、変更対象、順序の節は出典にできず、決定だけが支える基準は作らない。
  - 既存コードの振る舞いと禁止は、要求か既存の保証が支え、かつ `## Ground Review` の pre-mortem が変更で壊れうると挙げたものだけを基準にする。支えの無い今の振る舞いは基準にせず、今の実装を固めない。
  - 要求が入力の受け付ける範囲を広げるか変えるとき、要求の条件を満たさない入力が変更前に受けていた扱い (拒否、例外) を保つことを、要求とその入力の検査を出典にした非影響の `[振る舞い]` にする。要求が触れていない入力は変えない。
  - 要求が書いた肯定の構造 (〜を使う、〜で包む、〜に置く) と移行の途中の状態 (〜のまま動かす、まだ移していない) は、まず実装の選択を変えても成り立つ結果 (URL を開いた時に出る内容、できること。〜のまま は変わらない結果) の `[振る舞い]` にする。結果にできず、禁じる対象を探す pattern が書けるものは、`[禁止]` に直して基準にする (「`readSession` を使う」は「`readSession` 以外が `getCookie` を直接使わない」)。どちらにも直せないものは、実装の選択と移行の途中の状態か、判断の正本が決めて理由を書いたものなら実装の制約として範囲外に返し、それ以外は既定と行き先を添えて未決の判断にする。
  - 振る舞いを変えない改修の目的は `[禁止]` で書く (改名なら旧名が残らない)。書けなければ不足情報にする。
- 書いてよい名前: 基準と受け入れテストに書く名前は、外の境界の名前、仕様の節が名指しした名前、判断の正本が名指しした外の境界の名前、既存の試験の seam の名前 (結果を取り出すものに限る) だけにする。計画の実装案 (決定、作るもの、変更対象、順序などの節) が挙げる新しい関数、型、ファイルの名前は書かない。判断の正本にあっても内部の関数名は書かない。文書の置き場所は読み手との境界として書いてよい。`[禁止]` が禁じる対象として名指しする名前 (改名でなくす旧名、直接使わせない依存) は書いてよい。
- 判定できる基準: 範囲内の成功、失敗、境界、非影響の各条件を、独立の基準にする。境界はすぐ両側の観測で判定し、同一に見える必要があるケースは両者の観測を比べる基準にする。
  - 禁止と不在の範囲: `[禁止]` と不在 (0 件) を期待する基準は、書く前に、禁じたものを探す pattern を走査範囲に、未追跡のファイルも含めた `git grep -n -E` で現在のツリーに当て、変更前に当たる行を確かめる。当たった行を 1 行ずつ、計画が消す行と変更後も残る行 (計画が名指ししないが変更後も要る利用、計画が残す行、他の要求が残すと定める文書や作らせる試験) に分け、残る行が 1 行でもあれば、残る行に当たらないよう禁じる対象 (pattern) を絞るか、走査範囲を正の pathspec で絞る。除外の pathspec (`:!`、`:^`、`:(exclude)`) は書かない。リポジトリ全体の検索は未追跡も含めた `git grep` のように、`.gitignore` が無視する生成物を走査しない形で書く。
  - 文書の基準は、話題と置き場所 (識別子、見出し、ファイル) だけで観測する。計画の決定 (選んだ手順、値、仕組み) を文書の中身として基準に写さない。文は後の推敲で変わるので全文の一致は求めない。
  - 全条件を基準に MECE に対応付け、漏れ、重複、同時に成立しない組があれば書き直すか不足情報に分ける。
- 書く節: 計画の唯一の `## Acceptance Criteria` 節に、1 行 1 件の `- AC-NNN: [振る舞い] <本文> (出典: <出典>[, <出典>])` か `- AC-NNN: [禁止] <本文> (出典: <出典>)` (または `- [ ] AC-NNN: ...` の形) の行と空行だけを置く。出典は `R-n` か既存の保証のパスを `, ` で連結する。`[禁止]` の後にはあってはならないものを「〜を書かない」「〜を使わない」の形で書く。対応表や注記は別の `##` 節に置く。
- ID: 既存が無ければ `AC-001` から、あれば既存の最大より大きい番号を付ける。既存の基準は ID ごと保持し、意味が変わったものだけ旧 ID を再利用せず新しい ID の基準で置き換える。種類の印や出典を足すだけなら意味の変更に数えない。実装の名前を外して書き直した結果、観測するものが変わるなら意味の変更に数える。

## 網羅と Gate (`## MECE Review`)

- 追跡してから比べる: 基準に関わるコードは呼ぶ定義まで、共有定義は計画が名指ししないものを含むすべての呼び出し元・利用者まで、リポジトリ内で追い、辿り着いた定義にも同じ追跡を行う。計画が書く状態に別の状態との関係を定める仕様があれば、もう一方の状態を変える既存経路まで、計画が導入する設定値は、それを列挙する運用面 (設定サンプルなど) まで追う。追い終えた範囲を根拠として固定し、名指しされていない運用面は、覆ったと言うときに突き合わせた範囲を示す。
- MECE: 突き合わせるのは次の 3 つだけにし、対応 (ある、無い、矛盾、読めない) と欠落・重複・矛盾を名指しして挙げる。読めない・追えない根拠に依存する比較だけを未検証として範囲を示す。
  - 要求 → 基準: 全 `R-n` が 1 つ以上の基準の出典に挙がっているか。外から観測する手段が無い要求 (速く、読みやすく) は要求の表に `| R-n | 未検証: <理由> |` と書く。根拠が読めないことにはこの `未検証` を使わない。計画が扱わない要求は `| R-n | 範囲外: <理由> |` と書き、計画を直すか利用者がその要求を取り下げるまで進めない。計画が要求を二重に扱う項目は重複として挙げる。
  - 基準 → 出典: 各基準の出典が要求か既存の保証で、基準が出典の範囲を超えないか、要求を満たす実装の選択を変えても通るか (通らない基準は書き直す)。根拠が課す義務 (非同期処理の失敗や中断、共有定義の直接の利用者、境界の網羅、待つだけでは示せない不在) から基準へ逆に照合し、計画・基準・要求が扱うと確かめた点 (明示された範囲の宣言、観測の起点、所有する基準) を除いて、欠けだけを具体的に名指しする。経路の完了の証跡と、決定的な失敗シグナルか制御された seam が揃わない不在の主張は、根拠が欠けを支持するときに限り欠落、支持しなければ未検証とする。
  - 決定 → 要求: 計画の決定ごとに、仕える要求を決定の表 `| <決定の ID> | <R-n を ", " 連結> |` に書く。どの要求にも仕えない決定は `| <決定の ID> | 範囲外 |` と書き、範囲外の宣言を上流の修正として求める。要求の外の項目や段階 (後の Stage など) は、範囲外の宣言が計画に無いことを欠落とする。決定からは基準を作らない。
- 根拠: 過去の `## MECE Review` は根拠にしない。
- Gate: 根拠の比較だけから導く。根拠のある欠落・重複・矛盾が残るか、要求の表に範囲外の要求があるか、必要な上流の修正が 1 件でもあるか、必須の比較の根拠が欠けているか (計画の決定が要求を満たすかが依存先の振る舞いで決まり、その振る舞いを依存先の source か文書で確かめられないときを含む)、振る舞いを変えない改修の目的を `[禁止]` の基準で書けていないときは ready にせず、理由を書く。それ以外は ready とする。資料が決めていない値を依頼が決めるよう求めていることは、それだけでは ready を妨げない。
- 書く節: 計画の唯一の `## MECE Review` 節 (無ければ `## Acceptance Criteria` 節の直後に挿入) を、現在の AC-ID の集合を書く `- AC IDs:` 行と、`- Gate: ready` または ready 以外の値と理由を書く `- Gate:` 行 (各一つ)、`###` 以下の見出しのレビュー本文で置き換える。本文は要求の表、決定の表、指摘、必要な上流の修正を、確認済みの結果と未検証の範囲に分けて書き、本文の箇条を `- AC-` で始めない。
