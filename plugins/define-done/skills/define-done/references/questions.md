# 問い返し

- 起動: 依頼に「問い返し」の語があるときだけ、この規則に従う。このときは 3 段を最後まで行わず、契約・禁止・完了条件のうち計画、受け入れテスト、封の commit に関わるものの代わりにこの規則を使う。目的は、利用者が答えれば受け入れ基準を書ける状態まで要求を詰めることである。
- 入力: 計画のファイルは要らない。要求の引用元に、この会話で利用者が書いた文と、利用者が合っていると認めた AI の言い直しを加える。依頼や会話が名指しする計画、仕様、コードがあれば読み、名指しが無くても作業ディレクトリのコードと試験は読む。
- 調べ方: 1〜2 段の規則 (`references/requirements.md`、`references/acceptance-criteria.md`) に従って、要求を R-n として抜き出し、既存の保証と前提を確かめ、受け入れ基準を頭の中で下書きして網羅を確かめる。下書きはどこにも書かない。
- 問いにするもの: 次のどれかに当たり、資料も会話も決めていないものだけを問いにする。推測で埋めず、資料か会話が決めていることは問いにしない。
  - 受け入れ基準を書くのに要るが、資料が決めていない値 (境界ちょうどの扱い、上限、状態コード、判定の順序)
  - 要求どうしの矛盾と、要求と既存の保証 (試験、guard、不変条件を述べる文書) の食い違い
  - 2 通り以上に読める要求と、外から観測する手段が無い要求 (速く、読みやすく) の観測の仕方
  - 要求が頼る依存先の振る舞いで、source か外部状態を変えないコマンドで確かめられないもの
  - 計画があるときは、どの要求にも仕えない決定と、計画が扱わない要求
- 書き方: 1 件 1 問で、`- Q<n>: <問い>` の行の下に、`引用:` (対象の要求の原文と場所)、`決めない場合:` (利用者が決めないときの扱い。基準にしない、今の振る舞いを保つ、など)、`選択肢:` (資料か会話から言えるときだけ) を置く。既存の保証との食い違いは、その試験か文書のパスを引用に書く。
- 書かない: 計画、仕様、受け入れテスト、ほかのファイルを書かず、commit しない。
- 最終回答: 先頭に R-n を引用付きで 1 件 1 行で並べ、続けて問いを並べ、最後に問いの件数を書く。問いが 0 件なら「問いは 0 件」と書き、問い返しをせずに `/define-done <計画のパス>` を頼めば受け入れ基準と受け入れテストを作れると、計画のパスを書いて添える。
