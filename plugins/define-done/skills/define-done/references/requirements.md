# 要求と既存の保証

## 要求 (`## Requirements`)

- 段の目的: 後の段より先に、依頼が求めることを要求として抜き出す。受け入れ基準はこの要求か既存の保証だけを出典にするので、計画の決定がいくら変わっても受け入れ基準は変わらない。
- 引用元: 依頼の文、依頼や計画が名指しする issue・仕様・判断の正本 (ADR など)、計画の目的と背景の節だけから引く。計画の決定 (選んだ手順・値・仕組み、`D` と数字の ID の付いた項目)、作るもの、変更対象、順序、実装案の節からは引かない。
- 1 行 1 件: `- R-n: <要求> (「<引用>」 <場所>)` と書く。`<引用>` は引用元の文を原文のまま写し、要約も言い換えもしない。`<場所>` は `依頼`、`issue#<番号>`、`<repo からの相対 path>`、`計画:<見出しの文字列>` のどれかにする。
- 抜き出す単位: 依頼のうち、完了したときに成り立っているべきことを 1 件ずつ要求にする。依頼が文書 (runbook など) を書かせ、その文書で実現したい結果 (「回した secret が staging に反映される」など) も述べているなら、文書を書くことと結果を別の要求にする。結果の要求は振る舞いの基準で確かめ、文書の基準は話題と置き場所だけで確かめる。
- 要求どうしの範囲: ある要求 (「旧名が残らない」) の範囲を別の要求 (「移行の文書の旧名の言及は残す」「旧名が公開されないことを試験で確かめる」) が定めるときは、矛盾として扱わない。引用は原文のまま保ち、基準の範囲を絞って両方を満たす。
- 観測できない要求 (速く、読みやすく) も落とさずに要求にする。基準にできなければ、MECE レビューの要求の表に未検証として書く。
- 番号: `R-1` から振る。やり直しで意味の変わらない要求は番号を保つ。
- 書く節: 計画の唯一の `## Requirements` 節 (無ければ `## Ground Review` の前に挿入) に、要求の行と空行だけを置く。

## 既存の保証と前提 (`## Ground Review`)

- 根拠への結び付け: 現在の責務と信頼境界を提案された配置に対応付け、適合と衝突の結論をすべて、利用可能な要求と実装の根拠に結び付ける。範囲は提案が動かす責務と信頼境界に限り、既存コードの不具合探索は含まない。
- pre-mortem と反証: リポジトリが依存している保証を変更が壊す、または黙って無効にし得る具体的な経路を、設計文書が触れていないものも含め、漏れより過剰を優先して挙げる。テストとそのfixture、アーキテクチャやmigrationのwitness check、生成物、不変条件を述べるコメント、文書化された検証手順のように振る舞いを二次的に担うものも探り、設計の検証計画が変更対象に対するリポジトリ自身の確認を漏らしていれば、それも挙げる。挙げた各リスクを要求と実装の根拠で反証し、調べた上で反証できなかったものだけを残す。一部の範囲だけ反証できたら、その範囲を反証済みとして残りを残す。
- 前提の確認: 計画の新しい決定が頼る依存先 (ライブラリ、ツール、外部サービス) の振る舞いを挙げ、依存先の source (`node_modules` など repo から読めるもの) か、外部状態を変えないコマンドで反証する。決定の前提が成り立たなければ、衝突として具体的な帰結とともに挙げる。確かめられなければ未検証の結論に置き、その前提に要求の充足が懸かることを書く (MECE レビューは、これを必須の比較の根拠の欠けとして扱う)。
- 書く節: 計画の唯一の `## Ground Review` 節を置き換える。中身は境界の適合、前提の確認、重要なリスクと影響、反証したリスク候補とその根拠、推奨、未決の判断、未検証の結論。衝突と残ったリスクごとに、具体的な帰結と、提案が責務や信頼境界をどう動かすかを述べる。推奨と未決の判断を分け、未決の判断ごとに決めるのに要る根拠または選択を示す。アクセスできない根拠に依存する結論は、コードから推せる部分があっても断定せず、不足している根拠とともに未検証の結論にだけ置く。該当が無い項目は無いと書く。AC-ID はこの段ではまだ無いので引かない。
