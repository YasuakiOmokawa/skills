## 手順

1. 計画に `## Acceptance Criteria` の AC と `- Gate: ready` の `## MECE Review` が揃わなければ、準備せず、Verification Plan も作らず、足りない条件を報告して止まる。未確認の判断条件は、中身を創作せず、Gate を `ready` にするための不足条件として示す。
2. AC と MECE Review の根拠から、計画の作業項目を実行の依存順に並べ、各項目に変更対象、先行項目、紐づく AC、検証方法、未解決の前提条件 (推測で埋めない) を書く。MECE Review が特定した依存は明示して順序に反映する。
3. 計画に唯一の `## Verification Plan` 節を書き、既存があれば内容全体を置き換える。節は `- AC IDs: <現在の AC-ID を昇順で ", " 連結>` 行と、AC ごとに 1 つの `### AC-NNN` エントリだけから成り、各エントリは空でない `- Oracle:`、`- Evidence anchors:`、`- Prerequisites:`、`- Required effects:` を 1 行ずつ持つ。検証の意図はこの節にだけ置き、別の検証文書を作らない。
4. oracle は AC から導く。Evidence anchors にはリポジトリに実在すると確かめたファイル、関数、テスト、コマンドだけを書き、リポジトリ外の依存は anchor を創作せず Prerequisites に未解決として残す。
5. 前提が未解決でも、Required effects には oracle の観測に要る最小限の具体的な操作や状態変化を書き、未解決の点は Prerequisites に残す。これは後で要る承認の記述であって、承認を与えるものではない。
6. 不在、件数の上限、並行性、経過時間、非影響に基づく oracle は、経路と観測境界が完了した肯定的証跡と、決定的な失敗シグナルまたは制御された seam を Required effects が名指ししたときだけ、対応付けを完了とする。固定時間の待機だけなら、足りない肯定的証跡と失敗シグナルまたは seam を Prerequisites に未解決として残す。
7. 列挙した書き込み経路で確かめる不変条件は、関係するいずれかの状態の書き手が列挙の外に現れたら決定的に落ちる tripwire を Required effects が名指ししたときだけ、対応付けを完了とする。経路ごとの確認だけなら、tripwire の不足を Prerequisites に未解決として残す。
8. 書き込みは依頼が許可した計画にだけ行う。許可がない、または保存に失敗したときは、別の保存先へ迂回せず、書けなかったことを報告して内容を回答で返す。送信と再読取での確認を分けて報告し、確かめられない保存を成功と言わない。製品コードと外部状態は変えない。

## 完了

完全な計画、AC と検証の対応、書き込みの結果を返す。対応が未完の AC や未解決の前提条件があれば、部分的な完了として報告する。
