# 受け入れテストは既存のテストに倣い、凍結しない

define-done は受け入れテストを凍結の commit で守り、専用の入口 (土台) を通して書かせていた。その結果、taimei-auth には repo の規則に無い `acceptance/` と `acceptance/harness/`、既存の `*.e2e.ts` と違う `*.browser.ts`、独自の `playwright.config.ts` ができた。利用者は「define-done を走らせることで既存のテストコードの規則が壊れるのが一番嫌」と述べ、凍結については「仕様凍結しても別に後から仕様を崩すことが少なかった」と述べた。そこで凍結をやめ、受け入れテストを repo の既存のテスト (**手本**) と見分けがつかない形で書く。

- 置き場所、ファイル名の形、ランナーとその設定、補助、外の境界の通り方を手本から取る。既存のテストのファイルと補助のファイルに足してよい。
- commit を作らない。`check_done.py check` は、計画の整合、既存の行を変えていないこと、置き場所が HEAD にあること、実装の前に **規則の基準** が落ち **非影響の基準** が通ることを確かめる。
- 実装の完了は repo の test command が通ることで判定する。

## Considered Options

- 凍結を残し、土台を既存のディレクトリの新しいファイルに置く: 新しいディレクトリは無くなるが、受け入れテストは土台だけを import するので、中継するだけの補助がほぼ毎回できる。
- 凍結を残し、import の検査だけを外す: 補助は減るが、凍結したファイルは後から変えると改ざんになるので、既存のテストのファイルに足せず、テストは必ず新しいファイルになる。
- 完了を後から判定するコマンドを残す: AC とテストの対応を計画に 5 つ目の節として書く必要がある。防げるのは実装の途中で AC のテストが消されるか skip されることだけなので、採らなかった。

## Consequences

- 受け入れテストを後から弱めても検出しない。利用者はこのリスクを受け入れた。
- 内部の語彙を固定するテスト (Foldkit の Scene) が実装の変更で壊れた観測 (0001) への対策は、機械の検査から文の規則に変わる。手本から実装の選択を固定する試験を除き、外の境界を通る既存のテストが無い AC は未検証で返す。
- 画面の受け入れテストは、repo の既存の e2e と同じ通り方で書く。実サーバを通す repo では、エラーの応答や時間切れを作れない AC が未検証に回る。
- repo の test command がローカルで起動するもの (アプリのサーバを含む) は起動してよい。
- 新しいディレクトリは、repo の規則が求めるときと、依頼が名指しした置き場所が無いときだけ作り、理由を最終回答に並べる。
- この規則より前の凍結の commit と `acceptance/` のテストは、普通の commit と普通のテストとして残る。新しい版は凍結を読まない。
