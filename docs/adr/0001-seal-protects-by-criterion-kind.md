# 封の保護を AC の種類で分け、規約は AC にしない

封、土台、画面の受け入れテストの通り方は [0002](0002-acceptance-tests-follow-existing-tests.md) が置き換えた。AC を外から観測できる振る舞いだけにすること、種類の定義、規約を AC にしないことは残る。

taimei-auth で封を書き直した 14 本のうち、業務の要求が変わったのは 1〜2 本で、残りは AC が実装や移行の途中の状態や規約を固定していたか、受け入れテストが内部を通っていたためだった。そこで AC を外から観測できる振る舞いだけにし、実装の前に成り立たない **規則の基準** は封で恒久に守り、実装の前から成り立つ **非影響の基準** は **計画の完了** までだけ守る。種類は書き手が宣言し、封を作る時の実測と食い違えば封を作らない。コードにあってはならないもの (旧い `[禁止]`) は enforce-conventions の規約として担保する。規則の基準を恒久に残すため、define-done を使う repo は merge commit で取り込み、squash merge を repo の設定で禁じる。

## Considered Options

- 封の保護を計画の完了までに限る: 仕組みは最も単純で、過去の書き直しの 10/14 が不要になると計測したが、業務の規則を後から変えても記録が残らない。
- 一時的な AC を書き手の印や AC の文の言葉で見分ける: 書き手の判断に頼るか、「tag のまま出ない」のような恒久のセキュリティ規則を誤って失効させることを観測した。
- 封の時点の実測だけで種類を決める: 誤って最初から通るテストが黙って非影響の基準になり、何も観測していないテストの検出を失う。

## Consequences

- 作り替えだけの計画は非影響の基準だけになり、封の時点でも今も通れば完了する。
- 後の計画の要求が規則の基準を変えるときは、その計画の define-done が、要求の引用を根拠に古い基準を書き直して自分の封に含める。別の操作で検査を弱める道を作らない。
- 封の無い既存の業務規則は、それを変える計画が現れた時に、その計画の規則の基準として恒久になる。それまでは CI の回帰テストとレビューで守る。
- この規則より前の封は種類の記録が無いので、すべて非影響の基準として扱う。
- 受け入れテストは土台を通してだけ外の境界に触れる。土台が無い repo では define-done が要る分だけ作って封に含め、計画の完了まで守る。repo の前提条件として求めて Gate で止める案は、使い始めの手間が大きいので採らなかった。依存が無くて作れない部品が要る AC は、依存を足さずに未検証として返す。
- 画面の受け入れテストは、実ブラウザでビルド済みの画面を開き、通信の契約・認証ライブラリの公開 API・ブラウザの API だけを差し替えて書く。Foldkit の Scene は内部の Command と Message を語彙にするため、実装の変更で壊れることを観測した。
